## 1 引言

### 1.1 编写目的

本文档面向基于实时特征的个性化商品推荐系统编写，覆盖大数据链路的工程实现、系统设计与开发、工程规范与协作、数据业务价值挖掘、数据合规与安全五个方面的目标。

本文档定义基于实时特征的个性化商品推荐系统的功能需求、非功能需求、数据需求与接口需求，作为系统设计、开发、测试与验收的共同依据。文档力求每条需求可验证、可度量。

### 1.2 阅读对象

- 研发工程师
- 测试工程师
- 运维工程师
- 项目评审人

### 1.3 术语定义

| 术语 | 说明 |
|---|---|
| SPU | 标准产品单位，指商品表 `product` 中的一条商品记录 |
| SKU | 库存量单位，同一 SPU 下的具体规格；**价格字段位于此表** |
| 实时特征 | 由 Flink 滑动窗口从行为流计算、写入 Redis 的秒级统计量 |
| 用户画像 | 由 LLM 从用户行为序列总结的自然语言描述，再经向量化存入向量库 |
| 多路召回 | 从不同策略（向量 / 协同过滤 / 热门）各自取候选集的过程 |
| RRF | Reciprocal Rank Fusion，按排名倒数融合多路召回结果的算法 |
| 冷启动 | 用户无历史行为时的推荐场景 |
| 信息茧房 | 推荐结果过度集中于少数类目、导致用户视野收窄的现象 |
| 降级 | 依赖组件不可用时，切换到低质量但可用的替代路径 |
| 齐普夫分布 | Zipf 长尾分布，真实电商行为「少数商品占据多数交互」的统计特征 |
| DataForge | 本人开发的基于 LLM 的智能合成数据生成平台，本项目数据来源 |

### 1.4 项目背景

本项目在既有 B2C 电商系统「星创优品」基础上，将其静态运营榜单升级为千人千面的实时个性化推荐。系统需同时满足「实时感知用户行为」与「推荐结果可解释」两类目标，业务背景详见第 3 章。

## 2 项目概述

### 2.1 产品定位

一个面向电商场景的实时个性化推荐系统：一边用流计算实时感知用户行为变化，一边用「多路召回 + RRF 融合 + LLM 重排」生成带可追溯理由的推荐结果，并用离线指标量化验证推荐质量。

### 2.2 目标用户与干系人

| 干系人 | 关注点 | 对应需求 |
|---|---|---|
| 平台用户 | 首页是否推得准、有没有理由 | FR-17 推荐查询接口、FR-15 推荐理由生成 |
| 运营人员 | 推荐随行为变化的时效性 | FR-03 实时特征、G-2 生效延迟 |
| 数据分析 / 算法 | 推荐质量能否量化 | FR-22 离线评测、FR-23 消融实验 |
| 项目评审人 | 大数据链路完整性、工程规范、数据合规 | 第 6 章非功能需求、第 8 章验收标准 |

### 2.3 运行环境

| 组件 | 部署位置 | 说明 |
|---|---|---|
| 业务后端 | 宿主机 | Spring Boot 3.2.12 + MyBatis-Plus + Sa-Token，复用「星创优品」工程 |
| 实时计算 | 虚拟机集群 | Apache Flink 1.17.2，Standalone 模式 |
| 消息队列 | 虚拟机集群 | Kafka |
| 分布式存储 | 虚拟机集群 | Hadoop 3.3.4（HDFS），三节点 |
| 缓存与特征存储 | 宿主机 Docker | Redis |
| 向量库 | 宿主机 Docker | Qdrant |
| LLM / Embedding | 云端 API | DeepSeek（生成 / 重排）· DashScope（向量化） |
| 数据生成 | 宿主机 | DataForge（Java 21 + Spring Boot 3.5 + Spring AI） |
| 前端 | 宿主机 Nginx | Vue 3 三端，复用现有 |

### 2.4 假设与约束

- **假设**：DataForge 生成的数据分布合理，可用于推荐评测；LLM 与 Embedding 服务可用。
- **约束**：宿主机总内存 16 GB，是最硬的资源约束，决定虚拟机内存配置与分时启动策略（详见附录 A）。
- **约束**：集群 JDK 为 1.8.0_212，限制 Flink 版本上限。
- **约束**：所有实验为单机离线或准在线，不做真实高并发压测。
- **约束**：开发人力 1 人。

### 2.5 量化目标

| 编号 | 目标 | 度量方式 | 目标值 |
|---|---|---|---|
| G-1 | 推荐准确度优于静态榜单 | 离线 Recall@10 / NDCG@10，以热门榜为基线 | Recall@10 相对提升 ≥ 30% |
| G-2 | 推荐跟随行为实时变化 | 行为发生 → 推荐结果变化的时间差 | ≤ 5 秒（P95） |
| G-3 | 推荐结果可解释 | 带 LLM 生成理由的推荐条数占比 | 100% |
| G-4 | 冷启动可用 | 零行为用户能否得到非空推荐 | 100% |
| G-5 | 抑制信息茧房 | 类目覆盖率与多样性指数 | 不低于基线 |
| G-6 | 数据规模达标 | 行为数据总量 | ≥ 100 万条 |

> G-1 的基线数值需在实现 FR-22 离线评测后实测回填。

## 3 业务需求

### 3.1 业务背景

「星创优品」当前首页展示固定运营榜单（销量榜、上新榜），所有用户看到的顺序完全一致。这带来两个问题：用户面对同一份榜单需要逐条浏览才能找到感兴趣的商品；用户刚浏览或加购过某类商品，首页却不会发生变化——行为数据被采集后仅用于离线统计，没有回流到展示环节。

### 3.2 用户关注什么

| 关注点 | 对应数据 | 能看出什么 |
|---|---|---|
| 推荐是否合口味 | 行为流中的 `user_id` / `item_id` | 推荐结果是否被点击、加购、购买 |
| 推荐是否跟得上变化 | 行为的 `event_time` 与 `behavior_type` | 刚浏览过的类目是否出现在后续推荐中 |
| 推荐理由是否可信 | 用户画像文本 | 理由能否追溯到真实行为，而非空泛描述 |
| 商品口碑如何 | 评价表的 `rating` 与 `content` | 推荐的商品是否真的受好评，而非仅靠行为热度 |
| 类目是否太单一 | 商品的 `category_id` | 推荐结果的类目分布是否收窄 |
| 冷启动是否有结果 | 无行为用户 | 新用户是否拿到非空且合理的推荐 |

### 3.3 要解决的问题

- **个性化**：不同用户打开首页，看到的商品与顺序不同；
- **实时性**：用户行为发生后，推荐结果在秒级内反映该变化；
- **可解释性**：每条推荐给出可追溯到真实行为的理由；
- **防茧房**：推荐不因过度个性化而收缩到少数类目；
- **可量化**：推荐质量能通过离线指标与基线对比，而非主观判断。

## 4 数据需求

大数据项目的特色：数据需求是正文核心而非附录，因为「能算出什么指标」直接取决于「数据里有什么字段」。

### 4.1 数据来源与规模

本课题数据由本人开发的 **DataForge** 平台按「星创优品」真实表结构合成生成，不使用外部公开数据集。选择合成数据的原因有三条：

1. 公开数据集（如淘宝 UserBehavior）只有 `user_id` / `item_id` 等 ID，**不含任何商品文本**，无法支撑向量召回这一核心路径；
2. 合成数据可与真实表结构严格对齐，外键关联完整，评测链路无需额外做字段映射；
3. DataForge 支持齐普夫（Zipf）长尾分布，能够还原真实电商行为「少数商品占据多数交互」的分布特征。

| 数据域 | 目标规模 | 生成方式 |
|---|---|---|
| 商品域 | SPU 约 2 万条 · SKU 约 8 万条 · 类目 24 个 | DataForge LLM 模式（需语义质量） |
| 用户域 | 约 5000 个用户 | DataForge LLM 模式 |
| 行为域 | **≥ 100 万条**（目标 500 万条） | DataForge 零 LLM 展开模式 |
| 评价域 | 约 2 万条 | DataForge LLM 模式（评价文本需语义） |
| 订单域 | 由行为派生 | DataForge 派生表展开 |

### 4.2 数据生成的核心分工：语义用 LLM，规模用展开

DataForge 采用两阶段生成架构，这是本课题达成「百万级」的关键：

| 阶段 | 职责 | 是否调用 LLM | 吞吐量级 |
|---|---|---|---|
| 阶段一：语义样本生成 | 商品名、商品描述、品牌、用户名等**需要语义**的列 | 是 | 约 10 行/秒 |
| 阶段二：确定性展开 | 行为记录、订单记录等**无语义、只有 ID 与类型**的行 | **否（零 LLM）** | 本地代码执行，量级远超阶段一 |

**因此数据规模必须按列的类型分工，不能整体按同一量级要求**：

- **语义列**（商品名 / 描述 / 品牌）规模受 LLM 吞吐限制，2 万条 SPU 约需 30 分钟量级；
- **无语义列**（行为记录）走零 LLM 展开，百万级仅需分钟级。

> 若把「百万级」整体施加到语义列上，LLM 调用将耗时数十小时且成本不可控，属于方案上不可行的做法。这一点在设计文档中需进一步明确参数与限流策略。

### 4.3 商品域数据生成

| 表 | 列 | 生成模式 | 说明 |
|---|---|---|---|
| `category` | name | llm | 24 个类目 |
| `product` | name / description / brand | llm | 商品语义的主要来源，也是向量召回与推荐理由的文本基础 |
| `product` | category_id / first_category_id | pool | 引用 `category` 的主键池 |
| `product` | status / deleted | enum | 控制上架与逻辑删除 |
| `product` | shop_id | pool | 引用 `shop` 主键池 |
| `sku` | price / stock | valueRange | 价格需符合真实区间分布 |
| `sku` | product_id | pool | 引用 `product` 主键池 |

### 4.4 行为域数据生成

| 列 | 生成模式 | 说明 |
|---|---|---|
| `user_id` | pool | 引用 `user` 主键池 |
| `item_id` | **zipf** | 齐普夫长尾分布，还原「少数商品占据多数交互」 |
| `behavior_type` | enum | pv / cart / fav / buy，权重按真实电商比例配置 |
| `event_time` | 时间线生成 | 按事件时间递增，跨度需覆盖滑动窗口长度 |
| `category_id` | 派生 | 由 `item_id` 关联 `product` 派生，保证与商品侧一致 |

### 4.5 评价域数据生成

评价数据是本课题的**显式反馈来源**，其价值不止于"多一张表"，而是同时作用于画像、召回、重排三个环节。

| 表 | 列 | 生成模式 | 说明 |
|---|---|---|---|
| `product_review` | user_id / product_id | pool | 引用用户与商品的主键池 |
| `product_review` | rating | 加权枚举 | 1~5 星，分布需偏向 4~5 星（真实电商的评分分布特征） |
| `product_review` | content | llm | 评价文本，情感倾向必须与 `rating` 一致 |
| `product_review` | create_time | 时间线生成 | 必须晚于对应订单的创建时间，保证时序合理 |

**评价数据在推荐链路中的五个作用点**

| 环节 | 作用 | 对应需求 |
|---|---|---|
| 画像生成 | 评价文本是「用户喜欢什么、在意什么」最直接的表述，与行为序列一起输入 LLM | FR-06 |
| 协同过滤 | `rating` 构成显式评分矩阵，作为交互权重的增强项 | FR-10 |
| 商品索引 | 评价摘要可作为商品文本的补充语料，提升向量召回质量 | FR-26 |
| 重排与理由 | 商品平均评分作为质量信号，也用于生成「高分好评」类理由 | FR-15、FR-25 |
| 离线评测 | 高评分商品可作为评测集中正样本的补充来源 | FR-20 |

> **评分矩阵的稀疏性约束**：评价只能发生在有购买或加购行为的用户-商品对上，因此评分矩阵极度稀疏（2 万条评价对 5000 用户 × 2 万商品）。协同过滤的主数据必须是**隐式行为矩阵**（pv / cart / fav / buy 加权），评分只作为已评价用户-商品对的**权重增强项**——不能反过来把显式评分当作 CF 的主体数据来源，否则矩阵稀疏度会让 CF 失效。

### 4.6 字段与指标对照表（核心）

| 字段 | 类型 | 能支撑的指标 | 无法支撑的指标 |
|---|---|---|---|
| `user_id` | bigint | 用户维度全部指标、协同过滤、用户画像 | — |
| `item_id` | bigint | 商品召回、点击率、覆盖率 | — |
| `category_id` | bigint | 类目覆盖率、多样性指数、防茧房验证 | — |
| `behavior_type` | tinyint | 行为权重、转化漏斗、实时热门榜 | 停留时长类指标 |
| `event_time` | datetime | 实时性验证、时间衰减、趋势分析 | — |
| 商品 `name` / `description` | varchar | 向量召回、LLM 重排、推荐理由生成 | — |
| 商品 `price`（在 `sku` 表） | decimal | 价格敏感度画像、性价比推荐 | 促销价 / 历史价分析 |
| 评价 `rating` | tinyint | 显式反馈、CF 权重增强、商品质量信号 | 分项评分（物流 / 服务 / 描述相符） |
| 评价 `content` | text | 画像生成、商品索引补充语料、理由生成 | 细粒度情感归因 |
| **数据缺失**：商品图片 | — | 无法做多模态召回 | 图片相似召回 |
| **数据缺失**：用户人口属性 | — | 无法做人群定向 | 年龄 / 性别分群推荐 |
| **数据缺失**：曝光日志 | — | 无法计算真实 CTR | 曝光-点击转化率 |

> 该表明确了本课题的能力边界：数据里有什么，才可能算出什么。上表最后三行是**数据本身的缺失**，属课题边界声明的一部分（见第 9 章）。

## 5 功能需求

每条功能需求均为「可验证」写法，遵循「给[谁] + 用[什么数据] + 按[什么规则] + 达到[什么标准]」。

### 5.1 功能总表

| 编号 | 功能 | 需求描述（可验证） | 来源字段 | 优先级 |
|---|---|---|---|---|
| FR-01 | 用户行为采集 | 采集浏览 / 加购 / 收藏 / 购买四类行为，标准化为五字段事件写入 Kafka | user_id, item_id, category_id, behavior_type, event_time | 高 |
| FR-02 | 行为生成与加速回放 | 由 DataForge 生成百万级行为数据，按事件时间加速写入 Kafka，倍率可配置 | event_time | 高 |
| FR-03 | 实时行为特征计算 | Flink 滑动窗口计算用户近期行为特征，秒级写入 Redis 并设 TTL | user_id, item_id, behavior_type, event_time | 高 |
| FR-04 | 实时热门榜单 | 维护全站与分品类两份热门榜，分值随时间衰减 | item_id, category_id, behavior_type, event_time | 高 |
| FR-05 | 实时画像更新触发 | 行为去抖后投递画像更新消息，同用户 30 秒内多次行为合并一次 | user_id, item_id, event_time | 高 |
| FR-06 | 画像生成 | 用 LLM 将「行为序列 + 评价文本」总结为四段式自然语言画像 | item_id, behavior_type, event_time, rating, content | 高 |
| FR-07 | 画像向量化入库 | 画像文本经 embedding 后 upsert 到向量库，附带用户 ID 与生成时间 | 画像文本 | 高 |
| FR-08 | 画像时效管理 | 画像带时间戳，超期降权；用户注销时同步删除向量 | event_time | 中 |
| FR-09 | 向量召回 | 以画像向量检索相似商品，过滤已购 / 已加购 / 下架商品 | item_id, user_id | 高 |
| FR-10 | 协同过滤召回 | 以隐式行为矩阵为主、显式评分为权重增强，召回相似用户喜欢的商品 | user_id, item_id, behavior_type, rating | 高 |
| FR-11 | 实时热门召回 | 始终可返回非空热门候选，作为冷启动与降级兜底 | item_id | 高 |
| FR-12 | RRF 多路融合 | 按排名倒数融合多路召回结果，各路权重可配置 | — | 高 |
| FR-13 | LLM 重排 | 结合画像对候选集重排，只排序不新增商品 | item_id | 高 |
| FR-14 | 重排结果校验 | 出现候选集外商品 ID 判为无效输出，降级为 RRF 原始顺序 | item_id | 高 |
| FR-15 | 推荐理由生成 | 为每条推荐生成一句可追溯到用户行为的理由 | item_id, behavior_type | 高 |
| FR-16 | 多样性约束 | 同一类目占比设上限，负反馈商品强制排除 | category_id | 中 |
| FR-17 | 推荐查询接口 | 返回个性化商品列表（含理由与来源），LLM 失败自动降级并标记 | — | 高 |
| FR-18 | 首页个性化渲染 | 推荐区块与榜单区块并存，游客降级为热门榜且不展示空状态 | — | 高 |
| FR-19 | 负反馈处理 | 负反馈事件入流，商品立即降权并写入带 TTL 的排除列表 | user_id, item_id | 中 |
| FR-20 | 评测集构建 | 按时间切分训练 / 评测集，覆盖活跃用户与冷启动用户 | event_time | 高 |
| FR-21 | 指标计算 | 计算 Recall@K / NDCG@K / MRR / 类目覆盖率 / 多样性指数 | item_id, category_id | 高 |
| FR-22 | 离线评测报告 | 在同一评测集上与热门榜基线对比，输出指标报告 | — | 高 |
| FR-23 | 消融对比实验 | 四组对比：单路 / 双路 / 三路+RRF / 三路+RRF+LLM 重排 | — | 高 |
| FR-24 | Embedding 对照实验 | 相同评测集下对比不同 embedding 方案的检索质量 | — | 中 |
| FR-25 | 商品评分聚合 | 聚合每个商品的平均分与评分分布，作为召回与重排的质量信号 | rating | 中 |
| FR-26 | 评价文本入索引 | 商品索引文本由「名称 + 描述 + 评价摘要」构成，评价摘要由 LLM 从该商品评价中提炼 | content | 中 |

### 5.2 核心功能详细说明（FR-03 实时行为特征计算）

**输入**：Kafka 主题 `user-behavior` 的行为流

**窗口**：滑动窗口，长度与步长可配置（默认 10 分钟窗口 / 1 分钟步长）

**输出**：写入 Redis 的实时特征，key 格式 `feat:{user_id}:{metric}`，带 TTL

**业务规则**：

- key 必须带用户 ID 前缀与 TTL，避免键空间无限增长；
- Redis 写入失败时丢弃该条特征，**不得阻塞主链路**；
- 必须使用**事件时间**语义，不允许使用处理时间做窗口计算。

### 5.3 核心功能详细说明（FR-13 LLM 重排）

**输入**：RRF 候选集（商品名 / 类目 / 价格）+ 用户画像文本

**输出**：重排后的有序商品 ID 列表

**业务规则**：

- 提示词要求 LLM **只做排序与筛选，不允许编造候选集之外的商品**；
- 返回结果必须经 FR-14 校验，校验不通过降级为 RRF 原始顺序；
- 调用超时（默认 3 秒）即降级，不得让请求挂起。

### 5.4 核心功能详细说明（FR-16 多样性约束）

**输入**：最终推荐列表 + 商品的 `category_id`

**业务规则**：

- 同一一级类目在列表中的占比不超过设定上限；
- 已被负反馈的商品强制排除，且不参与补位；
- 该项约束在 LLM 重排**之后**执行——在保留 LLM 排序意图的前提下兜住信息茧房风险。

### 5.5 模块与需求映射

| 模块 | 覆盖需求 |
|---|---|
| M1 行为采集与实时特征 | FR-01 ~ FR-05 |
| M2 用户画像与商品索引 | FR-06 ~ FR-08、FR-26 |
| M3 多路召回与融合 | FR-09 ~ FR-12、FR-25 |
| M4 LLM 重排与理由 | FR-13 ~ FR-16 |
| M5 推荐服务与展示 | FR-17 ~ FR-19 |
| M6 离线评测与实验 | FR-20 ~ FR-24 |

## 6 非功能需求

### 6.1 性能

| 指标 | 要求 |
|---|---|
| 推荐接口响应时间 | P95 ≤ 800ms（含 LLM 重排）；纯召回路径 P95 ≤ 150ms |
| 行为到推荐生效延迟 | ≤ 5 秒（P95） |
| 实时特征写入延迟 | Kafka 到 Redis ≤ 1 秒 |
| 协同过滤召回耗时 | ≤ 100ms（走缓存） |
| 行为回放吞吐 | 峰值 ≥ 3000 条/秒（受单机 16GB 内存约束，按实测调整） |
| 数据规模 | 行为数据 ≥ 100 万条（目标 500 万条） |

### 6.2 容量

| 项 | 规模 | 说明 |
|---|---|---|
| 商品（SPU） | 约 2 万条 | 由 DataForge 生成，取代现有 300 条测试数据 |
| 商品（SKU） | 约 8 万条 | 价格字段所在表 |
| 类目 | 24 个 | 类目覆盖率指标的计算基数 |
| 用户 | 约 5000 个 | 演示用户规模 |
| 行为数据 | ≥ 100 万条 | 目标 500 万条 |
| 评价数据 | 约 2 万条 | 显式反馈来源，覆盖有购买 / 加购行为的用户-商品对 |
| 向量存储 | 商品向量约 2 万条 + 用户画像约 5000 条 | 维度 1024（Embedding 升级后） |

### 6.3 可靠性（含降级）

**不丢数据**：Flink 开启 Checkpoint，Kafka 消费位点可恢复。

**降级策略（必须实现）**：

| 故障点 | 降级路径 | 返回行为 |
|---|---|---|
| LLM 不可用或超时 | 降级为 RRF 排序结果 | 正常返回，标记降级 |
| 向量库不可用 | 降级为实时热门榜 | 正常返回，标记降级 |
| Redis 不可用 | 降级为数据库兜底查询 | 正常返回，标记降级 |
| 画像更新失败 | 保留上一版画像 | 不阻塞主链路 |

任一降级发生时接口必须正常返回，不允许直接报错。

### 6.4 安全性（含合规）

- **接口鉴权**：推荐接口需登录态校验（沿用 Sa-Token），未登录按游客策略返回热门榜；
- **越权防护**：推荐接口只返回当前登录用户自己的个性化结果，**不接受任意用户 ID 查询**；
- **凭证管理**：所有 API Key（DashScope / DeepSeek）与数据库密码通过环境变量注入，禁止明文写入配置文件或提交到 Git；
- **数据脱敏**：演示与文档中涉及用户标识时做脱敏处理；
- **不做敏感推断**：画像生成提示词禁止推断政治倾向、健康状况、宗教信仰等敏感属性；
- **数据来源合规**：数据由 DataForge 合成生成，不含任何真实用户信息。

### 6.5 可扩展性

- 召回层各路策略实现同一接口，新增召回策略不改融合层与上层；
- Embedding 以接口（`EmbeddingModel`）注入而非具体实现类，便于替换模型而不改业务代码；
- 推荐结果缓存键包含画像版本，画像更新自动失效，无需人工清理。

## 9 边界声明（本课题明确不做）

| 不做的事 | 原因 |
|---|---|
| 深度推荐模型（DIN / DeepFM / 双塔等） | 课题重点在实时链路与 LLM 编排，模型训练超出范围 |
| Spark ALS 离线训练 | 与"实时"的课题定位不匹配，单机训练成本高 |
| 多模态特征（商品图片向量） | **数据本身不含商品图片字段**（见 4.5） |
| 人群定向（年龄 / 性别分群） | **数据本身不含用户人口属性**（见 4.5） |
| 真实 CTR 计算 | **数据本身不含曝光日志**（见 4.5） |
| 线上 A/B 分流实验 | 无真实流量，评测全部走离线 |
| 模型在线学习 / 实时训练 | 只做实时特征，不做实时训练 |
| 推荐结果的商业化考量（广告、佣金等） | 与课题目标无关 |
| 改写 shop 现有用户体系与商品体系 | 复用现有能力，避免课题范围扩散 |
| 生产级高可用（多副本、容灾） | 单机演示环境 |

## 附录 A：资源约束与部署方案

### A.1 硬件基线（2026-09-21 实测）

| 项 | 实测值 |
|---|---|
| 宿主物理内存 | 15.73 GB |
| 宿主 CPU | 14 核 20 线程（6P + 8E 混合架构） |
| 磁盘 | 单块 SSD，D 盘剩余 100 GB |
| 虚拟机三台 | 现有配置每台 4 GB / 8 vCPU（**必须下调**） |
| Docker 容器 | ES 1.18 GB + RocketMQ 1.22 GB + Qdrant 0.10 GB + Redis / Nginx |
| WSL2 后端进程 | 1.2 ~ 1.5 GB，且默认**只涨不还** |

### A.2 分时启动方案

**阶段一：实时链路开发（虚拟机开机，ES 不停）**

| 项 | 分配 |
|---|---|
| Windows 基线 | 约 4 GB |
| WSL2 / Docker | 限 2.5 GB |
| hadoop102 | 3 GB / 4 vCPU |
| hadoop103 | 2 GB / 2 vCPU |
| hadoop104 | 2 GB / 2 vCPU |
| **合计** | **约 13.5 GB** |

**阶段二：在线推荐开发（虚拟机关机）**

| 项 | 分配 |
|---|---|
| Windows 基线 | 约 4 GB |
| WSL2 / Docker（Qdrant + Redis） | 限 2.5 GB |
| 本地 Embedding 模型（若采用） | 约 2.5 GB |
| **合计** | **约 9 GB** |

### A.3 必须执行的配置（按优先级）

1. **创建 `.wslconfig`**，限制 WSL2 内存上限为 2.5 GB 并开启自动回收。这是**必需项而非优化项**：当前该文件不存在，WSL2 使用默认值（上限为宿主的 50%，实测容器可见 7.62 GiB）且只涨不还。
2. **下调虚拟机内存与 vCPU**：`hadoop102` 内存 4096 改 3072 MB、`numvcpus` 8 改 4；`hadoop103` / `hadoop104` 内存 4096 改 2048 MB、`numvcpus` 8 改 2。vCPU 总数控制在 8 以内，避免被调度到 E 核造成性能抖动。
3. **勾选 `Fit all virtual machine memory into reserved host RAM`**，避免 VMware 将虚拟机内存换页到 `.vmem` 文件。
4. **Flink 采用 Standalone 模式**，省去 NodeManager 开销；在 2 GB 的 TaskManager 节点上这是决定性因素。
5. **本地 Embedding 模型不得与虚拟机集群同时运行**：仅在离线评测或数据准备时启动，用完立即退出。
