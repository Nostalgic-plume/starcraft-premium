# 智能客服提示词收口设计（意图分类 4 类 + 订单段落）

> 日期：2026-09-20　模块：`com.shop.rag`　类型：提示词/意图识别收口（L2）

## 一、背景：本轮要解决的两个语义冲突

上一轮已落地 5 项修复（闲聊意图分流、SaToken 预热、订单工作流回复与用户消息落库、Nginx SSE 透传、订单上下文注入 + SSE 心跳）。
实测后又暴露两处**提示词层面的语义冲突**，不是代码逻辑错，而是「提示词说反了」：

1. **分类器提示词只有 3 类，且把闲聊塞进 product 的兜底描述里**
   `CLASSIFY_PROMPT_TEMPLATE` 原文：「product：商品咨询/导购/**闲聊**——其余所有情况」。
   规则层已新增 `Intent.CHITCHAT`，但 LLM 兜底链只解析 `cancel/query/product`，**闲聊没有出口**。
   结果：「在干嘛」「你是deepseek吧」这类词表未覆盖的短句，被 LLM 分类成 product，闲聊又走回导购链路。

2. **订单兜底链注入订单数据后，商品列表恰好为空，主 prompt 把模型带偏**
   `buildOrderContext()` 注入「===== 用户订单信息 =====」段落时，`%s`（相关商品信息）占位符为空串。
   主 prompt 的「## 当没有商品信息时」正好命中，该节写着「追问用户具体想找什么类型的东西」
   → 用户问订单，模型反问「您想找什么类型的东西」，答非所问。

## 二、硬约束

1. **不增加 LLM 调用轮次**：分类兜底仍是「单次、非流式、8 秒超时、失败回 PRODUCT」。
2. **不改接口契约**：`POST /api/chat/ask` 入参出参、SSE 帧类型（`route`/`token`/`products`/`end`/`error`）全部不变。
3. **不削弱确定性优先级**：取消/查订单强信号词永远先于 LLM 兜底命中，规则层保持 0 延迟。
4. **兜底安全网不变**：LLM 失败或输出无法识别 → 回 `PRODUCT`。宁可多撞一次商品检索，也不能不回答。
5. **`route` 帧口径不变**：取值仍为 `chitchat` / `product` / `order_query` / `order_cancel`。

## 三、改动设计

### 3.1 分类器提示词扩为 4 类

| 类别 | 语义 | 判据 |
|---|---|---|
| `cancel` | 取消订单（写操作） | 用户明确要退单/取消某笔订单 |
| `query` | 查询订单（只读） | 问自己订单的状态/物流/买了什么 |
| `chitchat` | 闲聊 | 问候/道谢/告别/情绪倾诉/问你是谁/让陪聊，**且不涉及具体商品** |
| `product` | 商品咨询/导购 | 其余所有情况 |

配套：`classifyByLlm()` 解析链改为 `cancel → query → chitchat → product → null`。

**解析顺序不能倒**：分类器偶尔会输出解释性文本（如「这是 chitchat，不是 product」）。
按 `cancel → query → chitchat → product` 顺序短路匹配，才能保证 `chitchat` 不被尾部的 `product` 抢走命中。

### 3.2 兜底触发条件收紧：新增 `ambiguousShort`

新增常量 `AMBIGUOUS_MAX_LEN = 12`，规则③ 改为两个条件「或」：

```
orderDomainHit = 含「订单/单/快递/退/取消」
ambiguousShort = 长度 ≤ 12 且 不含商品信号词 且 不含闲聊词
orderDomainHit || ambiguousShort  →  调一次 LLM 分类
```

**完整触发矩阵：**

| 输入特征 | 触发 LLM | 结果 |
|---|---|---|
| 命中取消强信号词（取消/退单/退掉/不想要了/拒收/别发货…） | 否 | `ORDER_CANCEL` |
| 命中查订单强信号词（我的订单/物流/待发货/订单+进度…） | 否 | `ORDER_QUERY` |
| 命中订单域词（订单/单/快递/退/取消） | **是** | LLM 判定 |
| 短句（≤12 字）且无商品信号词、无闲聊词 | **是** | LLM 判定 |
| 命中闲聊词且不含商品信号词 | 否 | `CHITCHAT` |
| 其余 | 否 | `PRODUCT` |

**为什么用「短句」当门槛，而不是全量兜底**：门槛就是延迟。一次兜底约 0.5~1.5s，
若每轮都跑，「我想买个手机」也得先等分类。用语长 + 信号词做门，命中的只会是
「在干嘛 / 你是deepseek吧 / 哦这样啊」这类短闲聊，正常购物句基本都带信号词，不会被拖慢。

**阈值 12 怎么来的**：最短的商品句（「买个手机」4 字）必然含「买」，已被 `PRODUCT_SIGNAL_WORDS` 挡住；
能落进 `ambiguousShort` 的必然是词表未覆盖的极短句。取 12 上限是为了兜住「你是deepseek吧」（11 字）；
不再放大是为了防长句被 LLM 改判——长句本来就该走商品链路。

**`ambiguousShort` 为何要同时排除闲聊词**：命中了闲聊词，规则④ 已经能直接判 `CHITCHAT`，
再花一次 LLM 纯属浪费（`你好` 只有 2 字，若不在门里排除，每句问候都要多等一秒）。

### 3.3 主 prompt 新增「## 当有订单信息时」段落

插入位置：`## 当有商品信息时` 之后、`## 当没有商品信息时` 之前。内容：

- 下方含「===== 用户订单信息 =====」段落时，说明本轮问的是订单
- 直接依据该段落的真实数据回答（订单号、状态、商品、件数），**不要编造**
- **不要再说「看不到订单」，也不要让用户提供订单号**
- **不要推荐商品、不要追问「您想找什么类型的东西」**
- 用户想进一步处理某笔订单时，引导他直接说出订单号

同时在「## 当没有商品信息时」标题下补一行：
「（若下方已给出「用户订单信息」段落，本节不适用，按上一节的订单规则回答）」——
把两节的适用边界写死，避免模型自己猜哪节优先。

## 四、入参 / 出参

无变化。
`resolve(String message)`：入参用户原文，出参 `Intent` 枚举（**永不返回 null**，兜底失败回 `PRODUCT`）。
`POST /api/chat/ask`：`{"message": "...", "conversationId": "数字串"}` → SSE 帧流。

## 五、错误返回与降级

| 场景 | 行为 |
|---|---|
| 分类 LLM 调用超时（8s）或报错 | 记 debug 日志，返回 null → 调用方回 `PRODUCT` |
| 分类 LLM 输出无法识别 | 返回 null → `PRODUCT` |
| 订单上下文查询异常 | `buildOrderContext()` 返回空串 → 退化为「无商品信息」分支，不阻断回答 |
| 消息为空 | `resolve` 直接回 `PRODUCT`（Controller 层另有空消息拦截） |

## 六、容易踩的坑

1. **解析顺序**：`chitchat` 必须排在 `product` 之前，否则闲聊类永远命中不到。
2. **闲聊守门不能撤**：规则④ 是「命中闲聊词 **且** 不含商品信号词」，
   否则「你好，手机多少钱」会被误判成闲聊，白丢一次商品检索（已有守门单测）。
3. **`ambiguousShort` 的两条排除缺一不可**：漏排商品信号词 → 购物句被闲聊化；
   漏排闲聊词 → 每句问候都多一次 LLM 往返。
4. **`AMBIGUOUS_MAX_LEN` 按 `String.length()` 计**：中文 1 字符，emoji 占 2 个 char。
   带 emoji 的短句会略显「长」，最坏情况是多触发一次 LLM 分类，无功能风险。
5. **订单段落靠标记串识别**：模型按「===== 用户订单信息 =====」认段落，
   改这个标记串必须同步改 `ChatService.buildOrderContext()`，否则订单规则整段失效。

## 八、遗留（本轮未处理，另开）

1. **未登录访问 SSE 接口返回 500 而非 401**：`GlobalExceptionHandler` 返回 JSON，
   而请求 `Accept: text/event-stream`，Spring 抛 `HttpMediaTypeNotAcceptableException` → 500。
   属独立缺陷，需让异常处理器针对 SSE 请求返回 SSE 错误帧。
2. **`conversationId` 非数字**（如 `"default"`）→ `Long.valueOf` 抛 `NumberFormatException` → 前端只看到「服务异常」。
3. **前端 `FloatingChat.vue` 的 route 标签表缺 `chitchat`**，闲聊时状态条为空（需 `npm run build`，用户已声明先只做 Java）。
