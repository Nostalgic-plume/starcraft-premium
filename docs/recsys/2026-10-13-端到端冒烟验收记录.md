### 1.1 启动前提：内部调用凭证

`rec.internal-token`（推荐服务）与 `shop.rec.internal-token`（商城后端）**均从环境变量
`REC_INTERNAL_TOKEN` 注入且无默认值**。该变量原先不在 `.env` 中，本次补入
（`.env` 已在 `.gitignore` 中，不会入库）。

⚠️ **两侧取值必须一致**：不一致时推荐服务固定返回错误码 `1009`，商城后端将其视为调用失败
并始终走「上游兜底」——**表现为首页有商品、不报错**，极易误判为「推荐服务已正常工作但热度榜为空」。

### 1.2 启动命令

```bash
cd /d/claudecode/shop
set -a; source .env; set +a

# 推荐服务（8082，仅绑定回环地址）
java -jar shop-rec/target/shop-rec-1.0.0-exec.jar

# 商城后端（8080）
java -jar shop-server/target/shop-1.0.0.jar
```

> ⚠️ 重新打包前必须先停掉占用 `shop-1.0.0.jar` 的商城后端进程，否则
> `spring-boot-maven-plugin:repackage` 会因无法重命名 jar 而失败
> （`Unable to rename ... shop-1.0.0.jar to ...jar.original`）。

## 2 验证项与结果

### 2.1 榜单查询链路

| # | 请求 | 实际响应（关键字段） | 判定 |
|---|---|---|---|
| 1 | 直连 8082，带 `X-Internal-Token` | `degraded:"游客"`，`recallSource:"HOT"`，`price:6999.00` | ✅ |
| 2 | 直连 8082，**不带**凭证 | `{"code":1009,"msg":"内部调用凭证非法"}` | ✅ |
| 3 | 商城后端 `/api/home/rank`（游客） | `degraded:"游客"`，结构与 ① 一致 | ✅ |
| 4 | 商城后端 `/api/home/rank`（带用户登录态） | `snapshotId:"u131_1791860127_afe805"`，`degraded:"冷启动"` | ✅ |

**第 4 项的意义**：`u131` 即 `aikairui` 的用户标识（用户表 id=131），证明商城后端确实从登录态
解析出身份并经 `X-User-Id` 透传给推荐服务——推荐服务侧「不接收用户标识参数」的约定成立。
快照标识符合设计格式 `u{userId}_{epochSecond}_{md5[0:6]}`。

### 2.2 行为上报链路（M-01，内嵌商城后端）

| # | 场景 | 实际响应 | 判定 |
|---|---|---|---|
| 5 | 携带登录态上报，时间用**前端实际发送的 ISO 8601 带时区格式**（`2026-10-13T10:55:00+08:00`） | `{"code":200,"msg":"受理成功"}` | ✅ |
| 6 | 不带登录态 | `{"code":1002,"msg":"登录态缺失，不采集行为数据"}` | ✅ |
| 7 | 重复提交同一 `eventId` | `{"code":1005,"msg":"事件重复上报"}` | ✅ |

**第 5 项的意义**：前端埋点使用带时区的 ISO 8601 而非 `yyyy-MM-dd HH:mm:ss`，
此处专程用同一格式验证，确认后端可解析——否则埋点会**全量失败**且只在浏览器侧静默。

**第 7 项的意义**：这一条正是本轮修正「重试时复用同一 `eventId`」的验证依据。
若重试时重新生成标识，服务端无法识别为重复，将产生重复行为数据。

## 3 本轮修复的验证（对照）

### 3.1 兜底榜单补齐 price

| | `items[0]` 实际内容 |
|---|---|
| **修复前**（冒烟开始时，8080 为旧构建） | `{"itemId":"1","itemName":"华为 Mate 60 Pro...","mainImage":"...","recallSource":"NATIVE","score":0.0}` |
| **修复后**（重启后，同一请求） | `{"itemId":"1",...,"price":6999.00,"recallSource":"NATIVE","score":0.0}` |

**界面后果（修复前）**：`RecRankList` 按 `Number(item.price) || 0` 映射价格，
缺字段时**整屏推荐商品显示 ¥0**，且不报任何错误。

### 3.2 Long → String 序列化

| | 表现 |
|---|---|
| 修复前 | `itemId` 为 JSON number（如 `1`）；配置项主键、画像标识同理 |
| 修复后 | `itemId:"1"`、`id:"2109832926512750594"`（19 位雪花 ID） |

**修复前的影响**：19 位雪花 ID 超出 JS `Number.MAX_SAFE_INTEGER`（2^53-1），
`JSON.parse` 会悄悄改写末尾数字。榜单商品标识一旦失真，**点击卡片跳详情页必然 404**，
且浏览器控制台无任何异常提示。

> 补充观测：降级路径（商城后端 `nativeRank`）返回的 `itemId` 一直是字符串，
> 而推荐服务路径修复前是数字——同一字段的类型随降级与否漂移。
> 前端 `RankItem.itemId` 因此声明为 `string | number` 并在使用处统一 `String(...)`。

### 3.3 指标聚合方式

`/api/rec/metrics/catalog` 现返回 `aggregation` 字段（`avg` / `sum`）。
比率类指标（覆盖率、命中率）按 `avg` 聚合，避免看板把同小时的多条明细求和后
显示成「85% + 90% = 175%」。
