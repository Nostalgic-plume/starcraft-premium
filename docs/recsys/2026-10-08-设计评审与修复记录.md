## 1 前置决定：需求规格说明书作废

《需求规格说明书》（2026-09-20）自本次评审起**作废，仅存档**。

作废原因：该文档采用的是「语义召回 + 协同过滤 + 热门」多路召回路线，并包含商品向量索引、LLM 自然语言画像、推荐理由生成、负反馈与多样性约束、离线消融评测等能力；而概要与详细设计采用的是「类目偏好 + 热门」双路召回路线。两者不是同一条技术路线上的文档，需求规格中的多项要求在设计链中无对应实现。

处理方式：

1. 该文档头部加「已作废 · 仅存档」声明，逐条说明作废原因与现行基线；
2. 清理其余 4 份文档中对它的全部 5 处引用（概要 1.3、详细 1.2 与 2.5、精简版 1.2 与 2.5、需求分析 3 处）；
3. 需求分析说明书 1.1 与文末改写为指向概要与详细设计，并明确其自身为**现行需求基线**。

**由作废连带失效的 3 项原漏洞**：效果指标缺失（需求依据消失，转为主动补充项，见第 3 节）、过滤已购已加购（原为需求规格要求，需求分析无此条，转为体验增强项）、画像更新后缓存失效（需求分析无此要求）。

## 2 致命级问题（4 项，全部已修复）

### 2.1 灌数顺序未约束，水位线会丢弃全部历史事件

| 项 | 内容 |
|---|---|
| 问题 | 详细设计 3.2 规定水位线为「当前最大事件时间 − 10 秒」、迟到超 5 分钟丢弃；而 8.5 的灌数方案只约束了速率（分批 5000、约 2000 条/秒），**未约束顺序** |
| 后果 | 只要有一条时间靠后的事件先到达，水位线即被推高，此后所有更早的历史事件全部命中"严重迟到"被丢弃。表现为行为明细与消息消费均正常，但特征覆盖率趋近于 0，灌数校验直接失败；排查时极易误判为特征计算故障 |
| 修复 | 详细设计 8.5 新增「灌数顺序（强制）」行，要求按 eventTime 升序灌入并在脚本内断言时间戳单调不减、不满足即中断；新增专段说明该机制的原因与例外处理（确需乱序时临时调大迟到容限并标注）。3.2 与精简版同步 |
| 位置 | 详细 8.5、精简版 8.5 |

### 2.2 Redis 容量与淘汰策略双重不匹配

| 项 | 内容 |
|---|---|
| 问题 | 配置为 `maxmemory 512MB` + `allkeys-lru`，但分桶累加值全部驻留内存库，且小时桶保留 8 天、天桶保留 30 天 |
| 后果 | 按 1 万活跃用户估算，小时桶约 3840 万字段、天桶约 600 万字段，Redis 哈希每字段开销约 100 字节，**仅这两项就远超 512MB**；内存打满后 LRU 会淘汰"低频但高价值"的偏好特征键，导致后续请求大批量落入特征缺失降级 |
| 修复 | ① 分桶状态迁出内存库，改由 Flink 托管状态承载（见 2.3），保留时长收敛为分钟桶 2 小时、小时桶 48 小时、天桶 8 天，依据是 24h 档需 24 个桶、7d 档需 7 个桶，**与特征有效期 8 天对齐，原保留量属冗余**；② 淘汰策略改为 `volatile-lru`；③ 8.4 新增「内存占用核算（分桶迁出前后对比）」段，给出量化对比 |
| 位置 | 详细 4.2 / 6.1 / 8.1 / 8.4，精简版同步 |

### 2.3 Flink 只做搬运，未使用其事件时间与状态能力

| 项 | 内容 |
|---|---|
| 问题 | 原设计中 Flink 仅承担「读 Kafka → 写 Redis」的搬运工作：分桶累加由业务代码写 Redis 哈希、六档窗口由业务代码全量重算，事件时间语义与水位线并未真正使用；同时配置「状态后端为内存」，而 `MemoryStateBackend` 在 Flink 1.17 已废弃 |
| 后果 | 引入了 Flink 的部署与运维成本，却未获得其核心能力；窗口汇总为 O(维度数 × 桶数) 的全量重算，随用户行为增长而恶化；被追问「Flink 用在哪里、状态怎么管理、检查点怎么配」时无内容可答 |
| 修复 | 改为**真正使用 Flink**：分桶累加值下沉至 KeyedProcessFunction 的三个 MapState（各自配状态 TTL），状态后端改 RocksDB，检查点 60 秒、EXACTLY_ONCE，并行度与主题分区数对齐为 3，M-04 的商品热度算子并入同一作业；**窗口汇总改由处理时间定时器驱动、不依赖水位线推进**，并新增专段说明该选择与"5 秒时效"的关系（若改用事件时间窗口算子，延迟将拉长到 10 秒以上） |
| 附带约束 | Flink 1.17.2 仅支持 Java 8/11，与 Java 22 的在线服务编译目标不兼容，故 M-02 独立为 Maven 工程 `shop-rec-flink`（见第 5 节） |
| 位置 | 详细 3.2 / 3.4 / 4.2 / 8.1 / 8.2，概要 4.3，精简版同步 |

### 2.4 快照语义边界未定义，"5 秒实时"可能被 300 秒快照抵消

| 项 | 内容 |
|---|---|
| 问题 | 需求卖点是"行为后 5 秒内影响推荐"，而快照 TTL 为 300 秒；E-02 的 `snapshotId` 是可选参数，9.3 只写"分页或下拉加载（回传 snapshotId）"，**全文没有任何一处写明首屏请求不携带 snapshotId** |
| 后果 | 前端只要实现成"把上次的快照标识缓存起来、每次打开首页都带上"，用户的实时行为在 300 秒内不会体现在榜单上，**5 秒时效的核心卖点直接失效**；属于不写清就一定会踩的联调坑 |
| 修复 | 5.1.2 参数说明、6.5 复用判定、9.3 界面要素三处明确「首屏与下拉刷新不带 snapshotId（强制重算），仅第 2 页起翻页携带」；9.3 新增「首屏与翻页的调用约定（联调必读）」，并写入 5.4 商城侧改造清单 |
| 位置 | 详细 5.1.2 / 6.5 / 9.3 / 5.4，精简版同步 |

## 5 架构决策：是否需要微服务 / 是否需要 Maven 多模块

### 5.1 结论

| 部分 | 结论 | 理由 |
|---|---|---|
| 商城后端（含 RAG 等能力） | **不拆** | 单模块 153 个 Java 文件、约 1.3 万行、1 个启动类，远低于多模块的经验拐点；RAG 等能力是主进程内能力，共享 mapper/entity/service/统一返回，拆出需处理大量共享依赖且回归风险高 |
| 推荐服务（M-01、M-03~M-10） | **不拆**，作为 `com.shop.rec` 包并入商城单模块 | 与商城同为 Java 22 编译目标；且已是独立进程（8082），**进程边界的隔离强度本就高于 Maven 模块边界** |
| Flink 作业（M-02 与 M-04 商品热度算子） | **独立 Maven 工程 `shop-rec-flink`** | 硬约束：Flink 1.17.2 仅支持 Java 8/11，商城为 Java 22，一个 Maven 模块只能设一个编译目标 |

### 5.2 是否需要微服务

**不需要。** 判断依据是三信号框架：

| 信号 | 是否成立 | 说明 |
|---|---|---|
| 独立伸缩需求 | 否 | 单机、300 商品、1 万用户、演示级并发，全部组件同机 |
| 故障隔离需求 | 部分成立，但已用更便宜的方式满足 | 计算侧（Flink 作业）与在线侧本就分离部署，进程级隔离已达成；再加注册中心/网关/熔断组件属重复投资 |
| 独立发布 / 团队边界 | 否 | 单人或小团队开发，推荐能力集中在新模块，无多团队并行发布需求 |

现有形态是**模块化单体（商城后端内嵌 M-01）+ 一个独立服务（推荐服务 8082）+ 一个独立计算作业（Flink）+ 独立库（推荐库）**，这是本规模下最合适的形态，可称为"服务化拆分"，不必叫微服务。

**升级触发条件**（比"要不要"更有用）：

1. 推荐服务需要多实例水平扩容 → 将其无状态化（特征、快照全在 Redis，进程内只留兜底名单缓存）即可水平扩，**仍不需要注册中心**，Nginx 负载均衡足够；
2. 召回通道从 2 路扩到 5 路以上（向量召回、协同过滤、实时序列召回），且各路需不同语言或框架 → 此时才具备"按召回通道拆服务"的价值。**注意：需求规格原本就是多路召回，若后续要把向量召回加回来，这才是真正需要考虑服务化的时点。**

### 5.3 为什么"独立 Flink 工程"不等于微服务

Flink 作业独立工程解决的是**编译目标不兼容与部署单元不同**两个工程问题，不引入注册中心、服务发现、网关、分布式事务与跨服务远程调用——作业与推荐服务之间仅通过消息队列与内存库间接交互，无同步 RPC。这与微服务拆分的动机与代价完全不同。
