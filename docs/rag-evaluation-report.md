# RAG 检索离线评估报告

> 评估对象：`RagSearchService`（向量 + 关键词双路召回 → RRF 融合）
> 评估代码：`src/test/java/com/shop/rag/RagEvaluationTest.java`、`RagMetrics.java`
> 最近执行：2026-09-27（BGE-M3 迁移后复评，见 §9）

## 1. 评估目标

量化混合检索的召回质量，为「同义词扩展」「降级策略」两项改动的收益提供数据依据，
并沉淀一份可复现、可对比的基线。

## 2. 评估集构成

| 集合 | 条数 | 覆盖场景 |
|---|---|---|
| 基础集 | 30 | 商品名 / 品牌 / 品类 / 口语化 / 错别字 |
| 同义词集 | 5 | 口语说法 vs 商品用词（充电宝、刮胡刀、球鞋、充电头、笔记本电脑） |

标注方式：人工标注 `query → 期望商品 ID`，基于当前商品库（300 条，在售 278 条）。
指标实现见 `RagMetrics`。

## 3. 指标定义

- **Recall@K** = 前 K 名中命中的期望商品数 ÷ 该条期望商品总数，对全集合取平均 —— 衡量「找没找到」
- **MRR** = Σ(1 ÷ 首个命中排名) ÷ 期望商品数，对全集合取平均 —— 衡量「排得好不好」

例：`口红` 期望 4 个商品，实测命中排名 1、2，其余未进前 5
→ Recall@3 = 2/4 = 0.50，MRR = (1 + 0.5 + 0 + 0) / 4 = 0.375

## 4. 运行环境与复现

**依赖**（缺任一项测试自动跳过，不污染 CI）：

- MySQL 8：`shop` 库，FULLTEXT ngram 索引 `ft_product_search(name, description, brand)`，`ngram_token_size=2`
- Qdrant：`localhost:6333`(REST) / `6334`(gRPC)，集合 `products`（**1024 维** Cosine，2026-09-27 迁移后）
- 向量化：本地 TEI 容器 `shop-tei`（`http://localhost:9090/v1`，`BAAI/bge-m3`，1024 维）
  —— 2026-09-24 前为 DashScope `text-embedding-v1`（1536 维），历史数字见 §5 / §8

**命令**：

```bash
mvn test -Dtest=RagEvaluationTest
```

### 5.1 基础集 30 条

| 配置 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|
| 混合检索（生产配置，同义词开） | **0.639** | **0.722** | **0.482** |

### 5.2 同义词集 5 条（关闭 vs 开启扩展）

| 配置 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|
| 关闭扩展（baseline） | 0.567 | 0.767 | 0.443 |
| 开启扩展 | **0.800** | **0.867** | **0.532** |

与商品名用词 `移动电源` 的「移动/动电/电源」无交集，关闭扩展时「刮胡刀」Recall@5 = 0.000（完全漏召）。

### 5.3 降级链路实测（嵌入模型故障注入）

把 `DASHSCOPE_API_KEY` 置为无效值后重跑，触发 40 次 `[RAG降级]` 日志，测试仍通过：

| 场景 | 降级后实测 | 纯关键词单路（独立手算对照） |
|---|---|---|
| 基础集 | 0.678 / 0.719 / 0.469 | 0.678 / 0.719 / 0.486 |

修复前同场景返回全 0.000（整条商品搜索不可用）。详见 `docs/rag-fallback-design.md`。

## 6. 已知缺陷与边界

指标需结合以下边界阅读，避免误读。

### 6.1 评估集自身缺陷（4 处）

1. `id=137`「华为 MateBook 14 轻薄本」`status=0`（已下架），被检索链路的 `status=1` 过滤，
   任何路径都召不回 → 「笔记本电脑」用例召回上限被锁死在 2/3
2. 「小米」期望含 `14`，而 `14` 实为「苏泊尔 电饭煲 4L 球釜柴火饭」→ 标注错误
3. 「苹果手机」期望含 `31`，而 `31` 实为「苹果 AirPods Pro 2 主动降噪耳机」；
   库中真正的 `147`「苹果 iPhone 16 Pro Max 智能手机」反而未被标注 → 标注错误
4. 「进口水果」期望含 `52`，而 `52` 实为「京东超市 海南贵妃芒果」（国产）→ 标注错误

### 6.2 结构性边界

- 69 个期望位中 **32 个（46.4%）在原词关键字路上 MATCH 分数为 0**。
  多数是同义词/语义用例（属设计意图），但「床」是**单字**，
  在 `ngram_token_size=2` 下关键字路永远召不回，只能靠向量路
- 「手机」用例期望 `12`（小米 14 Ultra）、`16`（iPhone 15 Pro Max），
  二者名称与描述中**均无「手机」二字**（MATCH 分数 = 0），关键字路结构性不可达
- 「打游戏手机」「手鸡」（错别字）两例混合检索同样为 0，反映 `text-embedding-v1` 语义泛化能力有限

### 6.3 向量路并非总是增益

基础集上向量路反而**拉低**指标：关键字单路 Recall@3 = 0.678 > 混合 0.639。
典型如「运动鞋」0.50 → 0.00、「冰箱」1.00 → 0.00。
而在同义词集上向量路显著有益（0.333 → 0.567）。

**结论**：向量路的价值集中在语义/口语化 query；在字面匹配本就充分的 query 上会引入噪声。
后续可通过加权 RRF 或按 query 类型动态调权改善。

## 7. 后续可做

- 修正 6.1 的 4 处标注缺陷并重跑，保留「原版 / 修订版」两套对照，维持历史可比性
- 扩充评估集规模，并引入 NDCG 等排序敏感指标
- 评估更强的 embedding 模型（当前 `text-embedding-v1` 语义泛化偏弱）

## 8. 本轮改动对基线的冲击（2026-09-20）

本轮修复了「两路候选池不对称」缺陷：此前向量路结果被 `topK` 截断（本评估集用 `topK=5`，
即向量路最多只有 5 个候选参与 RRF），而关键词路取 `max(topK*5, 50)` 条 —— 两路候选规模不对等。

**因此 §5 的历史指标（Recall@3=0.639 / Recall@5=0.722 / MRR=0.482）不可与本轮之后的数字直接比较**，
必须先重跑「权重 1.0/1.0 + 候选池对齐」作为**新基线**，再与加权档位（1.0/1.5、1.0/2.0）比较，
否则「候选池」与「权重」两个变量会混在一起，无法归因。

同时，本节记录本轮顺带修复的两处契约缺陷（详见 `docs/rag-hybrid-tuning-design.md`）：
- 关键词路此前完全不过滤 `categoryId/minPrice/maxPrice`，与向量路语义不一致；
- 关键词路返回的 VO 不带 `minPrice/maxPrice`（纯关键词降级态前端价格为空）。

### 待执行的加权对照（需环境齐备后补跑）

前置：MySQL + Redis + Qdrant（`products` 集合已索引）+ DashScope Key 四件套在线。

实测时间：2026-09-20（JDK 22、Spring Boot 测试上下文、Qdrant `products` 集合 278 点、DashScope text-embedding-v1）。

| 权重（向量/关键词） | 基础集 Recall@3 | Recall@5 | MRR | 同义词集 Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|---|---|
| 1.0 / 1.0（新基线） | 0.628 | 0.761 | 0.487 | 0.833 | 0.867 | 0.536 |
| 1.0 / 1.5 | 0.678 | 0.728 | **0.511** | 0.833 | 0.867 | 0.536 |
| 1.0 / 2.0（推荐） | **0.711** | **0.764** | 0.504 | 0.833 | 0.867 | 0.536 |

逐条变化（基础集 Recall@3）：

| 查询 | wk=1.0 | wk=1.5 | wk=2.0 | 结论 |
|---|---|---|---|---|
| 苹果手机 | 0.50 | 1.00 | 1.00 | 改善 |
| 沙发 | 0.00 | 1.00 | 1.00 | 改善 |
| 冰箱 | 0.00 | 0.00 | 1.00 | 改善（仅高权重档生效） |
| 微单相机 | 0.50 | 1.00 | 1.00 | 改善 |
| 运动鞋 | 0.00 | 0.50 | 0.50 | 改善 |
| 精华 | 1.00 | 0.00 | 0.00 | **退化**（依赖向量路，权重≥1.5 即被挤出前 3） |
| 拍照手机 / 打游戏手机 / 手鸡 / 空调 | 0.00 | 0.00 | 0.00 | 不变 —— 召回层结构性缺失，调权重无效 |

结论：

1. 抬高关键词权重对基础集净收益为正（5 项改善 vs 1 项退化），**1.0 / 2.0 档综合最优**；
2. 同义词集三档数字完全一致：同义词扩展后的关键词路本就主导该类查询，权重不再是变量；
3. 语义类查询（「手鸡」「打游戏手机」）在所有权重下均为 0，印证「权重只改融合排序、改不了召回集合」——
   这类问题必须回到召回层（同义词表扩充 / 更强 embedding），不能靠调权重解决；
4. 与 §5 旧基线（0.639 / 0.722 / 0.482）相比，Recall@3 略降 0.011、Recall@5 升 0.039、MRR 升 0.005，
   差异来自候选池对齐（向量路候选由 5 条放开到 50 条）：召回更全、前 3 位噪声略增。
   故 §5 的数字自本轮起不再作为对比基准，一律以 1.0/1.0 新基线为准。

默认值已按本表结论调整为 **1.0 / 2.0**（写入 `application.yml` 的 `rag.rrf`）；代码内默认值与非法配置回退值仍为 1.0 / 1.0（等权），即配置缺失时行为与改造前完全一致、可随时回滚。
上线推荐档位 1.0 / 2.0 需显式配置。

预期方向（来自 §6.3 的旧结论）：抬高关键词权重对基础集有利、对同义词/语义集不利
（「手鸡」「打游戏手机」这类只有向量路能救），故必须分集合看，不能只看总平均。

本次复评回答迁移设计文档 `docs/rag-bge-m3-migration-design.md` §8 验收标准第 5 项：**检索质量是否不劣于基线**。

### 9.2 ⚠️ 基线怎么选（勿用 0.425 / 0.686 / 0.368 对比）

`Recall@3=0.425 / Recall@5=0.686 / MRR=0.368` 是 **Phase 2 时期**的数字
（`docs/superpowers/plans/phase2-rag/tasks.md`），当时尚未引入「候选池对齐」「同义词扩展」「加权 RRF」三项改动。

### 9.4 关键结论

1. **生产档（1.0/2.0）基础集 Recall@3 完全持平：0.711 = 0.711**；Recall@5 降 0.011、MRR 降 0.030。
2. **向量路获得语义泛化能力 —— 本次迁移的真正收益**：关闭同义词扩展时，「刮胡刀」`Recall@5`
   由 **0.000（完全漏召）→ 1.00**，「充电头」`Recall@3` = 1.00。关闭扩展态下关键词路无同义词可用，
   这些命中**只可能来自向量路**，证明 bge-m3 已理解「刮胡刀 ≈ 剃须刀」「充电头 ≈ 充电器」这类
   口语/书面词映射，而 text-embedding-v1 不能（§5.2 实测该 case 完全漏召）。
   含义：**硬编码同义词表这一 workaround 的边际价值下降**（扩展增益由 +0.233 收窄至 +0.167），
   系统对人工词表的依赖降低 —— 正是 §6.3 指向的「回到召回层（更强 embedding）」方向。
3. **同义词集三档权重不再等价**（0.733 / 0.767 / 0.767），而 text-embedding-v1 时期三档恒为 0.833
   （§8 结论 2 称「权重不再是变量」）。说明向量路在同义词 query 上的候选竞争力上升，
   已能挤进融合后前 3 名 —— 与结论 2 自洽。
4. 「拍照手机」改善：0.00 → 0.33（§8 该 case 在所有权重档均为 0.00）。

### 9.5 统计显著性与混淆变量（读数字前必看）

- **样本量**：基础集 30 条，单条权重 `1/30 ≈ 0.033`。MRR 差异 0.030 ≈ **0.9 条 query 的名次浮动**，
  Recall@3 差异为 0。在 30 条样本上此量级不足以支撑「提升/回退」判断，只能判定为**持平**。
- **混淆变量（方向对本轮不利）**：§8 基线测于 2026-09-20，当时 `ft_product_search` 为
  `(name, description, brand)`；品牌主数据迁移（`main/resources/db/migrate-brand-20260927.sql`，2026-09-27）
  删除 `product.brand` 列后，**FULLTEXT 索引自动变为 `(name, description)`**，关键词路少一个匹配字段。
  实测：278 条在售商品中 **270 条（97.1%）的品牌词已存在于 name/description**，仅 8 条仅存在于 brand 列，
  其中 4 条落在评估集期望 ID 内（2「口红」、44「扫地机器人」、205 / 236「球鞋」）。
  即本轮关键词路略弱于基线，**BGE-M3 真实表现应略好于上表**。
- 品牌迁移**不改变索引语料**：`UPDATE product SET brand_id = b.id WHERE p.brand = b.name` 按品牌名逐字回填，
  `ProductIndexer` 取 `brand.getName()` 与原 `product.getBrand()` 内容等价（空值 → 空串亦一致）。
- **未做隔离实验的取舍**：DashScope Key 仍有效（实测返回 1536 维），理论上可切回 + 重建 1536 维集合复跑，
  得到变量完全隔离的基线。未做，原因：① 额度 10 月到期，属回滚专用资源；② 上述混淆变量方向明确、
  量级仅 4/54 期望位；③ 不足以改变「持平」这一结论。

### 9.6 决策：不回退

依据：① 生产档 Recall@3 持平、差异处于噪声量级；② 向量路语义泛化能力明确增强（架构收益，
非指标波动可覆盖）；③ 对比偏差方向对 BGE-M3 不利；④ DashScope 额度 10 月到期，回退路径本身不可持续。

**保留观察项**：同义词集 Recall@3 降 0.066（等价于「充电宝」第 3 名商品掉到第 4 名，`Recall@5` 仍为 1.00）。
若后续扩充评估集后该趋势放大，优先排查 RRF 融合排序，而非更换 embedding。

**修复建议（未执行，属独立优化）**：§6.1 的 4 处标注缺陷仍未修订，其中 `id=137` 已下架导致
「笔记本电脑」召回上限锁死在 2/3，会持续压低同义词集指标。
