# 向量索引对账设计（集合一致性 + 内容陈旧检测）

> 状态：设计稿（2026-10-18）
> 关联：`docs/rag-candidate-cleanup-design.md`（幽灵索引的检索侧兜底）、`docs/rag-id-only-retrieval-design.md`
> 目标：补上「索引更新失败后永久陈旧、且无人知晓」的缺口

## 一、现状与问题

### 1.1 索引更新是「尽力而为」

所有 `productIndexer.addOrUpdate / remove` 的调用都包在 try-catch 里，**失败只 WARN、不阻断主流程**
（`ProductServiceImpl` 三处）。DB 写入与索引更新也**非事务**。

后果分两类：

| 失效类型 | 现状 | 已有防线 |
|---|---|---|
| **幽灵索引**（下架/删除后索引未删） | 检索时可能返回不可售商品 | ✅ 候选池清洗实时过滤（2026-10-17） |
| **漏建 / 内容陈旧**（上架或改内容后索引未写成功） | **商品永久搜不到，或搜到旧内容** | ❌ **无任何防线** |

第二类是本次要解决的：它不会报错、没有日志、只能靠人发现「这个商品明明在售却搜不到」。

### 1.2 为什么不用失败重试队列

重试队列只能覆盖「调用抛异常」这一种情况，覆盖不了：

- 进程在 DB 写入与索引更新之间崩溃（调用从未发生）
- 索引写入成功但内容基于旧数据（并发编辑时后写覆盖前写）
- 历史遗留的不一致（改造前就存在的）

**对账（reconcile）是通用的：不关心不一致是怎么产生的，只关心「现在是否一致」。**

## 二、方案

新增定时对账任务，做**两层**比对：

### 2.1 集合对账

```
MySQL 应索引集 = { id | status = 上架 ∧ deleted = 0 }
Qdrant 现存集   = 集合内所有 point 的 payload.productId
```

- `MySQL 有、Qdrant 无` → **漏建** → 重建
- `Qdrant 有、MySQL 无`（已下架/删除/不存在）→ **多余** → 删除
- `两边都有` → 进入内容对账

### 2.2 内容对账

payload 新增 `updateTime`（epoch millis），与 MySQL `product.update_time` 比对：

- 不一致（或 payload 缺失该字段）→ **陈旧** → 重建
- 一致 → 跳过

用 **epoch millis** 而非格式化字符串：避免时区/格式/精度差异导致的误判。
同一转换函数在写入侧与对账侧共用。

### 2.3 阈值保护（硬约束）

若差异总量（漏建 + 多余 + 陈旧）超过 `max(应索引数, 现存数) × maxAutoFixRatio`（默认 20%）：

- **只告警、不自动修复**
- 理由：大规模差异通常意味着环境异常（Qdrant 刚被清空、MySQL 连接异常导致查询不完整），
  此时自动修复可能变成"大规模误删/误建"

### 2.4 与重建互斥

索引全量重建会**先删集合**，此时对账会看到「全部漏建」。
阈值保护天然拦住（100% > 20%），无需额外锁；但日志需能区分这种情况（输出「可能正在重建」提示）。

## 三、硬约束

1. **不阻塞检索**：对账在定时任务线程执行，不进入检索链路。
2. **差异超阈值只告警**，不得自动修复。
3. **Qdrant / MySQL 任一不可用 → 本次跳过**（不修复、不误判）。
4. **单个商品修复失败只计数，不中断整轮**。
5. **幂等**：同一轮重复执行结果一致。
6. **`updateTime` 用 epoch millis**，写入侧与对账侧共用同一转换。
7. **开关可控**：`rag.reconcile.enabled` 默认 `true`，出问题可一键关闭。

## 四、入参与出参

### `QdrantCollectionHelper`（新增）

```
Map<Long, Long> scrollAllProducts()
  入参：无
  出参：productId → payload.updateTime（可能缺失，缺失时不放入或值为 null）
  分页：scroll API，每页 scrollBatchSize（默认 256），直到 next_page_offset 为空
  异常：Qdrant 不可用 → 返回空 Map（调用方按「跳过对账」处理）
```

### `IndexReconcileTask`（新增）

```
void reconcile()
  出参：无（结果写日志）
  日志：应索引数 / 现存数 / 漏建 / 多余 / 陈旧 / 修复数 / 是否因阈值跳过
```

### `IndexReconcileProperties`（新增，`rag.reconcile.*`）

| 配置 | 默认 | 说明 |
|---|---|---|
| `enabled` | true | 总开关 |
| `fixed-rate-ms` | 1800000 | 执行间隔（30 分钟） |
| `max-auto-fix-ratio` | 0.2 | 差异比例超过此值只告警 |
| `scroll-batch-size` | 256 | Qdrant scroll 每页条数 |

## 五、错误返回

| 场景 | 行为 |
|---|---|
| Qdrant 不可用 | 返回空 Map → 本轮跳过，WARN |
| MySQL 查询异常 | 本轮跳过，WARN |
| 差异超阈值 | 只告警，不修复 |
| 单商品补建失败 | 计入「修复失败」数，继续下一个 |
| payload 无 `updateTime`（旧索引） | 判为陈旧 → 重建（首次升级会全量被判陈旧，被阈值保护拦住，需手动重建一次） |
| 集合为空且 MySQL 有商品 | 视为「可能正在重建」→ 阈值拦截，告警中注明 |

## 六、容易踩的坑

1. **首次升级必须重建一次索引**：存量 payload 没有 `updateTime`，第一次对账会把全部商品判为陈旧，
   而阈值保护会拦住修复。**升级后先手动 `POST /api/admin/rag/rebuild`，再让对账接管。**
2. **不要把 `updateTime` 格式化成字符串**：`LocalDateTime.toString()` 的精度/时区差异会导致
   每轮都误判为陈旧，进而每轮全量重建。
3. **阈值比较的基数**：用 `max(应索引数, 现存数)` 而非「现存数」——当 Qdrant 被清空（0）时，
   分母为 0 会让比例计算失真。
4. **scroll 的分页终止条件**：`next_page_offset` 为 `null` 才结束，不能用「本页不足 batch」判断
   （Qdrant 可能返回满页但仍未结束）。
5. **对账与正常写入并发**：对账补建/删除与 `ProductServiceImpl` 的增量更新可能同时发生，
   双方都是幂等的 upsert/remove，最终一致；不需要锁。
6. **逻辑删除的商品**：`deleted = 1` 不在 MySQL 应索引集，若 Qdrant 仍有 → 按「多余」删除。

## 七、不做的事

- **不做失败重试队列**（对账已覆盖所有不一致来源，且更通用）。
- **不做 outbox 模式**（需要新表 + 调整事务边界，收益与复杂度不匹配）。
- **不做分布式锁**（单实例部署；多实例时需改为 Redis 锁，届时再加）。
- **不实时对账**（高频全量比对成本高，定时足够）。
- **不改检索链路**（幽灵索引的检索侧兜底保留，两层防护）。

## 八、验收标准

### 单元测试（离线）

- 集合一致 → 不产生任何修复调用；
- 漏建 → 调 `addOrUpdate`；
- 多余 → 调 `remove`；
- `updateTime` 不一致（含 payload 缺字段）→ 调 `addOrUpdate`；
- 差异超阈值 → **不产生任何修复调用**，且输出告警；
- Qdrant 不可用（空 Map）→ 跳过，不修复。

### 编译与回归

- `mvn clean test-compile` 通过；既有 42 个用例全绿。

### 真实链路

1. 重建索引（让 payload 带上 `updateTime`）；
2. 手动制造三种不一致各一例（改 DB 内容不动索引 / 删一个 Qdrant 点 / 往 Qdrant 加一个不存在商品的点）；
3. 触发对账（缩短 `fixed-rate-ms` 或手动调用），确认三类都被修复；
4. 检查日志输出各计数。

**不一致的制造方式**（可复现）：

```sql
-- ① 陈旧：改内容时间但不动索引
UPDATE product SET update_time = NOW() WHERE id = 151;
```
```http
### ② 漏建：直接删掉 Qdrant 点
POST /collections/products/points/delete  {"points": [61]}

### ③ 多余：写入一个不存在商品的假点
PUT /collections/products/points  {"points":[{"id":999999,"vector":[...1024维...],"payload":{"productId":999999,"updateTime":123}}]}
```
