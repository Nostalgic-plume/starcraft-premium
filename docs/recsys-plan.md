## 1 交付目标与完成定义

### 1.1 交付目标

在星创优品商城之上交付一个可运行的个性化推荐子系统：用户行为经消息队列进入 Flink 作业产出实时偏好特征，查询时走「类目偏好 + 热门」双路召回、融合过滤、加权重排，返回个性化榜单；全链路 7 种降级状态保证任何异常都返回非空榜单；配套离线评测产出可归因的效果指标。

### 1.2 完成定义（DoD）

全部满足才算完成，缺一不可：

- [ ] 详细设计 9.4 验收表**逐行**通过，每行有对应证据（日志、指标值、截图）
- [ ] 详细设计 9.5 评测报告产出：五组配置 × 全部指标，含 G1→G2→G3 的增益归因
- [ ] 压测报告含 P95 与 P99（榜单 P95 ≤800ms、P99 ≤1.5 秒；上报 P95 ≤100ms）
- [ ] 故障注入全覆盖：凭证非法、特征读取失败、召回异常、缓存异常、强制降级开关、服务不可用，均返回非空列表且 degraded 状态正确
- [ ] 商城侧改造完成并通过冒烟：上报 → 查询 → 改配置 → 回滚
- [ ] 代码入库，`mvn compile` 与 Flink 作业打包均通过

| **依赖** | 无（起点） |

| **易踩的坑** | ① 错误码不得自定义新码；② 配置默认值必须内置，不能因 Redis 不可读而报错；③ 键模板直接字符串拼接，不引入键前缀配置 |

### T2 M-01 行为采集与上报链路 · 1 天

| 项 | 内容 |
|---|---|
| **目标** | 打通数据入口，保证行为事件可靠进入消息队列且不阻塞页面 |
| **依赖** | T1 |
| **产出物** | E-01 `POST /api/rec/behavior/report` + 详细设计 3.1 的 10 步处理链（身份解析 → 参数校验 → 商品存在性校验 → 幂等去重 → 限频 → 无效事件与爬虫判定 → 采样 → 投递 → 异步落库 → 排除清单维护 → 返回）+ 8 类异常分支 |
| **验收方式** | 构造重复上报、事件时间越界、爬虫来源、限频超限四类事件，断言均被静默丢弃且 `t_pipeline_metric` 有对应计数；压测上报接口 P95 ≤100ms；断言投递失败时降级为直接落库且接口仍返回 200 |
| **易踩的坑** | ① 投递与落库绝不能阻塞返回，接口必须在 100ms 内返回；② 爬虫判定必须叠加"duration 非空采集率 ≥ 50%"前置条件，否则共用出口网络下会整片误杀真实用户（详细设计 3.1 步骤 6）；③ `rec:exclude:user:{userId}` 的写入只针对购买与加购，失败仅记日志不阻塞 |

### T3 shop-rec-flink 工程 + M-02 特征计算 + M-04 热度算子 · 2 天

| 项 | 内容 |
|---|---|
| **目标** | 交付实时特征计算链路，这是整个系统实时性的来源，也是本次架构调整的核心 |
| **依赖** | T1（配置键与分桶键格式约定） |
| **产出物** | ① 独立 Maven 工程 `shop-rec-flink`（**编译目标 Java 11**，仅引入 Flink、Kafka 连接器、Redis 客户端，不依赖商城任何模块）；② M-02 的 KeyedProcessFunction（三个 MapState 分别承载分钟桶/小时桶/天桶 + 各自状态 TTL）；③ 处理时间定时器驱动的汇总节流（200ms 合并）；④ 六档窗口汇总 + 偏好分合成 + 双重封顶；⑤ M-04 的商品热度算子（同作业内按商品键控的独立分支）；⑥ 水位线、检查点、RocksDB 状态后端配置 |
| **验收方式** | 灌入乱序事件，断言事件归入**其事件时间对应的**时间桶（而非到达时间）；断言修改 `duration` 不影响偏好分；断言作业重启后从检查点恢复、已写入特征仍可读；断言行为产生后 5 秒内特征可被读取；检查点连续成功、无失败告警 |
| **易踩的坑** | ① **编译目标是 Java 11**，与商城工程（Java 22）不可合并构建；② **窗口汇总必须用处理时间定时器，不能用 Flink 事件时间窗口算子**——后者要等水位线推进才产出，会把 5 秒时效拉长到 10 秒以上（详细设计 3.2 专段）；③ 状态 TTL 是 Flink 侧配置，与 Redis 键有效期无关，不要混用；④ 商品维度缓存为空时事件走侧输出流暂存，不要直接丢弃 |

### T4 M-03 画像 + M-04 维度/索引/兜底 + 定时任务 · 1.5 天

| 项 | 内容 |
|---|---|
| **目标** | 交付所有批处理产物：画像、商品维度、可售状态、热度榜、类目索引、兜底名单 |
| **依赖** | T1、T3 |
| **产出物** | ① M-03 画像任务（近 30 天行为、取模分 8 片、每批 1000、行为 <3 条不生成、Top5、版本号 yyyyMMdd、同事务切换有效性、裁剪至 3 版）；② 画像版本回滚 **E-08**（含 4004 错误码）；③ M-04 全量加载 / 增量刷新 / 对账三入口 + 可售判定 + 状态缓存；④ 类目候选索引（每类目前 200 名）+ 兜底名单（热度前 100，30 秒重建）；⑤ 6 个定时任务按详细设计 8.2 的 cron 配置 |
| **验收方式** | 模拟任务失败，断言旧画像与旧索引仍可读、不被覆盖；经 E-08 执行一次回滚，断言下一请求读到目标版本；目标版本超出保留范围时返回 4004 且当前版本不变；断言任务 1 与任务 2 不重叠、任务 3 与任务 4 错开 5 分钟；misfire 不补跑 |
| **易踩的坑** | ① 任务失败必须"沿用上一版"，绝不能清空或覆盖已有缓存；② 有效性切换必须在同一事务内，保证同一用户只有一个有效版本；③ 回滚接口要做幂等（目标版本已是有效版本时直接返回成功） |

### T5 M-05 / M-06 / M-07 召回·过滤·打分 · 1.5 天

| 项 | 内容 |
|---|---|
| **目标** | 交付在线查询的核心业务逻辑，也是个性化效果的实际来源 |
| **依赖** | T1、T3、T4 |
| **产出物** | ① M-05 双路召回（特征读取 30ms → 冷启动判定 → 两路并行 → 配额计算 → 截取 → 单路有效性校验）；② M-06 融合与过滤（合并去重 → **六类过滤**：上下架库存、黑名单、近 N 天已购已加购、地域不可售、会员限定、低质商品 → 兜底补位 → 分类统计）；③ M-07 重排（池内 min-max 归一化 → 加权求和 → 三级排序 → 固定坑位注入） |
| **验收方式** | 注入类目路超时，断言返回 degraded=召回降级且榜单非空；关闭特征读取，断言退化为热度序且 degraded=特征缺失；构造用户近 N 天已购商品，断言不出现在结果中（排除天数置 0 时复测为出现）；断言归一化遇到 max==min 时取值 0.5 不抛异常 |
| **易踩的坑** | ① 单路异常必须隔离，不得影响另一路；② 所有超时、权重、配额、TTL 必须走配置，**代码中不得出现裸数字常量**；③ 冷启动判定按详细设计 6.6 判定表四行逐行实现，不可简化 |

### T6 M-08 查询编排 + M-09 配置 + M-10 可观测 · 1.5 天

| 项 | 内容 |
|---|---|
| **目标** | 交付对外唯一出口与全部支撑能力：编排、快照、降级状态机、配置热更新、指标采集 |
| **依赖** | T5 |
| **产出物** | ① M-08 E-02 接口（凭证校验 → 身份判定 → 参数校验 → 快照命中 → 编排 → 生成快照 → 三段式返回 + 800ms 总超时中断）；② 降级状态机（按 7.2 优先级从命中的条件中取最严重者，对外只暴露一个状态）；③ M-09 E-03/E-04 接口 + 校验 + 副本同步 + 30 秒热更新 + `degrade.force` 三重防护；④ M-10 环节埋点 + 9 项指标 + 每小时汇总 + 阈值预警；⑤ 详细设计 9.3 的界面要素清单交前端 |
| **验收方式** | 逐条故障注入（凭证非法、特征读取失败、召回异常、缓存异常、强制降级开关、服务不可用），断言均返回非空列表且 degraded 为对应状态；改打分权值后 30 秒内生效且服务不重启；`degrade.force` 到期后自动复位并记录日志；断言首屏请求（不带 snapshotId）每次重新计算、翻页请求（带 snapshotId）返回一致顺序 |
| **易踩的坑** | ① 降级返回的 **HTTP 状态必须为 200**，降级信息只走 degraded 字段，否则前端会进错误分支；② `degrade.force` 必须权限分离 + 30 分钟自动复位 + 生效期间告警，三者缺一即是生产事故；③ 特征覆盖率分母要排除冷启动用户，否则新用户一多必然误报；④ 空集合与异常必须区分处理 |

| 项 | 内容 |
|---|---|
| **目标** | 把推荐子系统接进商城，并产出数据准备与效果验证两套脚本 |
| **依赖** | T6 |

## 4 风险与应对

| 序号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | **Flink 1.17.2 + Java 11 环境**（最高风险） | 作业无法提交或运行时报版本错误 | T3 优先启动，先用最小作业跑通"Kafka → 状态 → Redis"再补业务逻辑；确认运行镜像自带 JDK 11；作业工程编译目标锁 Java 11 |
| 2 | 单机 16GB 内存不足 | 组件互相挤占，作业或服务被 OOM | 按详细设计 8.1 的资源分配启动，分桶迁出后 Redis 压力已大幅下降；压测阶段实测水位并按 8.4 阈值调参 |
| 3 | 灌数顺序踩坑 | 特征覆盖率趋近 0，误判为计算故障 | 脚本内强制排序 + 单调性断言，不满足直接中断（详细设计 8.5） |
| 4 | 效果指标不达预期 | 无法证明系统价值 | 先跑通 G0 基线建立参照；按详细设计 6.4(7) 的三项杠杆调参（候选池规模优先）；评测价值定位于"链路正确性 + 增益可归因"，不承诺硬性百分比 |
| 5 | 三项预留过滤规则缺字段 | 按需求分析 3.4 逐条核对会缺项 | 已在概要设计 5.4 明确"本期不纳入验收"并给出启用条件，验收时按新口径执行 |
| 6 | Flink 作业状态规模超预期 | 检查点变慢、恢复时间变长 | 按 8.4 优先缩短小时桶与天桶保留时长，其次按单用户字段数上限清理最旧分桶键 |

## 5 每次提交前自检清单

从详细设计的硬约束中提取，用于代码评审自查：

- [ ] 时间口径：窗口归属、迟到判定一律用 `eventTime`，无一处使用到达时间
- [ ] `duration` 字段全局搜索，只允许出现在无效行为判定处，无第二处引用
- [ ] 降级状态枚举只有 7 个取值，未新增或改名；降级返回的 HTTP 状态均为 200
- [ ] 空集合（链路正常无数据）与异常（链路故障）在所有调用点均已区分处理
- [ ] 在线查询链路无重试逻辑，超时即降级
- [ ] 用户身份只来自服务端透传的 `X-User-Id`，未从请求参数取值
- [ ] 凭证（数据库、Redis、Kafka、`X-Internal-Token`）全部来自环境变量，配置文件只有占位符
