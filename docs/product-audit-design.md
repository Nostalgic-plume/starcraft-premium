# 商品审核流程 — 设计文档

> 2026-10-13 · 分支 `feat/eval-dataset-regen` · 状态：待实施
> 关联：[product-edit-design.md](./product-edit-design.md)（上一批商品编辑补全）

## 一、问题背景

`ProductConstants.STATUS_PENDING = 0`（待审核）在常量类里定义了、数据库列注释写了、前端状态下拉框也有这一项，**但正常业务流程走不到它**：

- `ProductServiceImpl.addProduct` 第 104 行强制 `setStatus(STATUS_ON_SHELF)` —— 商家新增即上架
- 全库 303 个商品中，12 条 `status=0` **全部来自 mock 数据**，无一条由业务流程产生
- 前端商家端状态框在新增时 `:disabled`，还贴着"新增商品默认在售"的说明

即：**审核机制是"装饰性"的** —— 有状态、有界面、有列注释，就是没有流程。

### 为什么不能只改 `addProduct` 一行

把 `addProduct` 改成 `setStatus(STATUS_PENDING)` 看似就够了，但**审核会立刻形同虚设**：

`PUT /api/merchant/product/status/{id}` 的权限是 `product:status`，而**商家角色持有这个权限**（`CLAUDE.md`：merchant = `product:add/edit/status`）。商家新增后自己调一次状态接口设成 `1`，就绕过了审核。

**所以必须同时收紧商家的状态修改权限**，这是本次改动的核心，也是它不能算"一行改动"的原因。

## 二、目标

1. 商家新增商品 → 进入「待审核」，用户端不可见
2. 管理员审核 → 通过（上架）或驳回（下架）
3. **商家无法自行把商品改成上架**（本次关键约束）
4. 保留商家的正常经营能力：主动下架、修改信息后重新送审

## 三、商品状态机（本次改动后）

```
                    ┌─────────────────────────────────────┐
                    │                                     │
   商家新增 ──────► 0 待审核 ──管理员审核通过──► 1 上架 ──商家主动下架──► 2 下架
                    │                          │              │
                    │                          │              │
                    └──管理员驳回──────────────┴──────────────┘
                              ↓                              │
                          2 下架 ◄───────────────────────────┘
                              │
                              └──商家重新提交审核──► 0 待审核
```

### 允许的状态流转

| 流转 | 谁可操作 | 说明 |
|---|---|---|
| `(新增) → 0` | 商家 | 新增商品自动进入待审核 |
| `0 → 1` | **仅管理员** | 审核通过，商品上架 |
| `0 → 2` | 仅管理员 | 审核驳回 |
| `1 → 2` | 商家 / 管理员 | 主动下架 |
| `2 → 0` | 商家 / 管理员 | 重新提交审核 |
| `2 → 1` | **仅管理员** | 管理员直接上架 |

### 禁止的流转

| 流转 | 拒绝理由 |
|---|---|
| **`任意 → 1`（商家发起）** | 「商品上架需管理员审核」—— 这是审核流程成立的基石 |
| 状态值不在 {0,1,2} | 「非法的商品状态」 |

> **设计取舍**：为什么允许商家 `2 → 0`（重新送审）而不是直接 `2 → 1`？
> 因为下架可能是因商品信息有误，重新上架理应再过一次审核。若允许商家随意上架，审核就退化成"只卡第一次"。
>
> **代价**：商家下架后想恢复销售，必须等管理员审核，是一个**运营成本**。若你的业务不接受这个成本，可改为"仅限制首次上架"（`0 → 1` 禁商家，`2 → 1` 放商家），实施时告诉我。

| # | 约束 | 说明 |

| C6 | **mock 数据兼容** | 库里 12 条 `status=0` 的商品**保持不动**，它们正好演示"待审核"在管理后台的表现 |

## 五、入参 / 出参

接口路径与参数**全部不变**，只改语义与校验：

| 接口 | 变化 |
|---|---|
| `POST /api/merchant/product/add` | 落库 status 由 `1` 改为 `0`（返回体不变） |
| `PUT /api/merchant/product/status/{id}` | 商家传 `status=1` 时抛 `BusinessException("商品上架需管理员审核，请提交审核后等待审核通过")` |
| `PUT /api/product/status/{id}` | 不变（管理员可任意流转） |

### 错误返回

| 场景 | code | 提示 |
|---|---|---|
| 商家试图上架 | 400 | 商品上架需管理员审核，请提交审核后等待审核通过 |
| 状态值非法 | 400 | 非法的商品状态 |
| 商品不存在 | 400 | 商品不存在 |

## 七、容易踩的坑

1. **`isLogin()` 而非 `hasRole()`**
   商家数据隔离拦截器已经因为 `hasRole()` 递归踩过坑（`CLAUDE.md` 明确记载）。判定商家身份一律 `StpShopUtil.INSTANCE.isLogin()`。

2. **管理员新增商品不应被误伤**
   `ProductController.add()` 的权限是 `PRODUCT_ADD, type="admin"`——**管理员新增的商品是否也要进待审核？**
   答案：**不进**。管理员新增即上架（他自己就是审核方，没必要自我审核）。
   → `addProduct` 里需按登录端分支设置初始状态。

3. **前端禁用 ≠ 后端拒绝**
   把"在售"选项置灰只是体验优化，**必须同时**在 Service 层拦截，否则直接 curl 就绕过了。

4. **商家改自己已上架商品的库存/信息，不应触发审核**
   编辑接口（`updateProduct`）**不碰 status**，所以不受影响。别顺手在编辑里加状态校验。

5. **mock 数据的 12 条待审核商品**
   改动后它们会真实出现在管理后台的「待审核」筛选里 —— 这是**预期行为**，正好用来演示审核流程，不要清理掉。

## 八、验收标准

| # | 验收项 | 方式 |
|---|---|---|
| A1 | 商家新增商品落库 `status=0` | 实测 + 查 DB |
| A2 | 新增的商品用户端不可见 | `GET /api/product/detail/{id}` 应查不到 / 列表不出现 |
| A3 | 商家自己上架被拒 | `PUT /merchant/product/status/{id}?status=1` → 400 + 指定文案 |
| A4 | 管理员上架成功 | `PUT /api/product/status/{id}?status=1` → 200，商品上架 |
| A5 | 商家下架自己商品仍可用 | `?status=2` → 200 |
| A6 | 管理员新增商品直接上架 | 走 `POST /api/product/add`，落库 `status=1` |
| A7 | 前端提示与禁用正确 | 商家端「在售」被禁用、「待审核」提示语正确 |
| A8 | 编译 + 构建双绿 | `mvn package` + `npm run build` |
