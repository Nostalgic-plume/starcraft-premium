# 首页信息流改造设计（无限滚动 + 首位个性化配额）

- **日期**：2026-10-14
- **范围**：首页由「分页商品网格」改为「无限滚动信息流」；推荐结果前 N 位改用纯个性化召回
- **关联**：《详细设计说明书》3.5~3.8（召回/融合/重排/查询）、6.3、6.4；需求分析 4.3「行为后 5 秒内影响推荐」

---

## 一、需求与边界

**要做什么**

1. 首页主内容区不再用分页组件，改为一直往下滑的无限滚动
2. 推荐结果**前 N 位（默认 5）来自类目偏好路**（纯个性化），其后位次走原有融合排序

**不做什么**

- 不改召回比例（`recall.ratio` 保持 70:30）
- 不改打分公式（`0.6 × 类目偏好 + 0.4 × 热度`）
- 不做「真无限」——候选池仍为 `recall.pool.size`（200），**这是硬上限**，见下文硬约束
- 不给分类侧边栏做推荐流（它只是筛选入口）

---

## 二、硬约束（改动前必须知道）

| # | 约束 | 说明与后果 |
|---|---|---|
| **C1** | **候选池 200 条 = 上限** | 快照的 `items` 最多 200 条（`recall.pool.size`）。前端 pageSize=20 时约 10 屏滑到底。**「无限滚动」实际是「长列表滚动」，滑到底必须给明确终止态**，不能无限循环追加——追加要靠重算新快照，而候选池不变，去重后几乎无新增。 |
| **C2** | **快照 TTL 300 秒** | 首屏/换一批不带 `snapshotId`（重算）；翻页带 `snapshotId` 复用同一快照保证顺序稳定（`SnapshotService`，配置项 `cache.result.ttl`）。长会话滑动会超过 300 秒 → 快照过期 → 下一次翻页**重算** → **顺序突变、出现重复**。本设计把该值调到 **1800 秒**。 |
| **C3** | **固定坑位优先级最高** | `RankService.rank()` 的步骤是 `打分 → 排序 → toRankedItems → injectFixedSlots`，**坑位注入在最后且会覆盖指定位置**。故首位个性化配额必须排在坑位注入**之前**：运营配置的坑位可以覆盖算法安排的位置。 |
| **C4** | **冷启动/游客没有个性化候选** | 游客走 `guestRank()`，根本不进个性化流程；冷启动用户的 `rec:feat:user:{id}:cat` 为空 → 类目偏好路召回为空。**「前 5 必须个性化」只能实现为「尽量」**：不足 N 条时用融合顺序补足，不允许留空位。 |
| **C5** | **类目偏好路候选有上限** | `recall.category.topN=3` × `recall.category.limit=50` = 最多 150 条，再经六条过滤规则后可能不足 N 条。同 C4，按「尽量」处理。 |
| **C6** | **合并后已分不出「来自哪一路」** | 融合阶段按商品 id 去重合并，但 `FilteredCandidate.sources` **保留了来源集合**，`RecallCandidate.SOURCE_CATEGORY_PREF / SOURCE_HOT / SOURCE_FALLBACK` 可用。配额实现依赖该字段，**不可回退成按分数判定来源**。 |

---

## 三、方案

### 3.1 首位个性化配额（后端，M-07）

**插入点**：`RankService.rank()` 中 `toRankedItems(scoreItems)` 之后、`injectFixedSlots(ranked)` 之前。

**算法**

```
输入：ranked（已按融合总分降序）、quota N（配置 rank.head.personalized.size，默认 5）
输出：重排后的 ranked

1. N <= 0 或 ranked.size() <= 1  → 原样返回（关闭开关）
2. 切分：head = ranked 中 recallSource == CATEGORY_PREF 的前 min(N, 该来源总数) 条
        rest = ranked 中除 head 之外的其余条目（保持原相对顺序）
3. 输出 = head ++ rest
4. head 不足 N 条时不补空位——剩余位次由 rest 自然填充（即 C4/C5 的「尽量」语义）
```

**为什么是「按融合分从类目偏好路里取前列」而不是「按类目偏好原始分重排」**

- 类目偏好路的候选**本来就是按该路召回分排序进入融合的**，取前列即取该路最靠前的商品；
- 若改为按 `categoryRaw` 重排，会绕开热度的 40% 权重，让前 5 位完全脱离热度校验，冷门商品可能被顶上来；
- 复用已有融合分还保证了 **head 与 rest 的打分口径一致**，只是「谁占前 5 位」不同。

**配置项**

| 键 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `rank.head.personalized.size` | int | 5 | 首位个性化配额条数；0 = 关闭，读不到时用 `RecConfigKeys.DEFAULTS` |

**⚠️ 本步骤有意打破「总分降序」不变量**

`sortItems` 建立的「总分降序 → 热度降序 → 商品标识升序」在**配额之后不再全局成立**：第 N 名的融合总分可能低于第 N+1 名（因为它来自类目偏好路而被提到前面）。

这是**需求要求的**（前 N 位必须是纯个性化），不是缺陷。但必须写明，否则后人对照 `RankService` 的「排序稳定性」注释会误判为 bug 并"修好"它。

`injectFixedSlots` 之后同理——坑位商品的分值为 0，却排在首位。

### 3.2 首页无限滚动（前端）

**`RecRankList` 由横向卡片行改为竖向信息流**

| | 现状 | 改后 |
|---|---|---|
| 布局 | 横向滚动卡片行 + 跑马灯 + 箭头翻页 | 竖向列表（每行若干张卡片，响应式） |
| 加载 | 「换一批」按钮 + 「加载更多」 | 首屏自动加载 + **触底自动加载**（IntersectionObserver） |
| 快照语义 | 首屏/换一批不带 snapshotId；翻页带 | **不变**（这是「5 秒内生效」与「顺序稳定」的取舍，不能动） |
| 终止态 | — | `hasMore=false` 时显示「没有更多了」并停止观察 |

**`Home.vue` 商品网格去分页**

- 移除 `<n-pagination>`
- 改为触底追加：`page` 递增，结果 `concat` 而非覆盖
- 保留分类侧边栏（筛选条件变化时重置列表与页码）

**关键实现约束**

- 触底用 `IntersectionObserver` 观察列表尾部哨兵元素，**不用 `scroll` 事件**（滚动事件逐帧触发，长列表下会拖慢主线程——本仓库 `RecRankList` 已有节流注释记录过同类教训）
- 组件卸载时必须 `observer.disconnect()`，否则路由切换后观察器泄漏
- 防重入：请求进行中不得再次触发加载（用 `loading` 标志 + 哨兵在加载中暂停观察）
- 去重：追加时按 `itemId` 去重，避免快照边界处出现重复卡片

### 3.3 配置调整

| 配置项 | 现值 | 改为 | 理由 |
|---|---|---|---|
| `cache.result.ttl` | 300 | **1800** | C2：长会话滑动必须让快照活过整个会话 |

> 该值是**数据**（`shop_rec.t_rec_config`）不是代码，改完立即生效（30 秒内热更新）。代码侧 `SnapshotService` 的兜底默认值同步改为 1800，避免配置缺失时退回 300。

## 四、入参与出参契约

**接口不变**：`GET /api/rec/home/rank?pageNum&pageSize&snapshotId`

| 参数 | 变化 |
|---|---|
| `pageNum` / `pageSize` | 不变。前端 `pageSize` 由 8 提到 **20**（长列表减少请求次数） |
| `snapshotId` | 不变。首屏/换一批不传；触底续接必须回传首屏的 `snapshotId` |
| 响应 `hasMore` | 不变，前端据此决定是否继续观察哨兵 |
| 响应 `items[].recallSource` | **新增可见变化**：首屏前 N 条的 `recallSource` 应为 `CATEGORY_PREF`（冷启动/游客除外）——这是本功能的验收特征值 |

---

## 五、错误返回与降级

| 场景 | 行为 |
|---|---|
| 配额配置读不到或非法 | 用默认 5；`< 0` 视为 0（关闭） |
| 类目偏好候选不足 N 条 | 有多少用多少，其余位次由融合顺序补 —— **不留空位、不报错** |
| 类目偏好路召回失败 | 沿用既有降级：该路丢弃，`degraded` 升级为「类目偏好召回异常」，配额自动退化为纯融合 |
| 冷启动/游客 | `degraded` 为「冷启动」/「游客」，配额不生效，全部走融合或热门 |
| 触底加载失败 | 保留已加载内容，尾部显示「加载失败，点击重试」，**不清空列表** |
| 快照过期（滑动超过 TTL） | 服务端重算新快照并返回新的 `snapshotId`，前端按 `itemId` 去重后追加；顺序可能变化，属已知取舍 |

## 六、容易踩的坑

1. **坑位覆盖**：把配额逻辑写在 `injectFixedSlots` 之后会「看起来生效、实际被坑位覆盖」。必须在之前（C3）。
2. **前端把 `snapshotId` 用错**：触底续接若不带 `snapshotId`，服务端会**重算**，导致滑到第二屏就顺序大变。首屏拿到 `snapshotId` 后必须一直回传，直到「换一批」才清空。
3. **`total` 与 `hasMore` 语义混淆**：`total` 是当前快照的条目数（≤200），不是全站商品数。触底终止条件用 `hasMore`，不要用 `total` 去和商品总数比。
4. **Long → String**：`itemId`/`total` 后端序列化为字符串，前端比较去重前要统一 `String(...)`（本仓库已踩过：排行榜 `itemId` 类型会随降级路径漂移）。
5. **轮播残留**：`RecRankList` 现有跑马灯/箭头/`scrollLeft` 逻辑在竖向列表下全部失效，必须**整段移除**而不是留着不调用——残留的 rAF 循环会持续申请帧。
6. **观察器未断开**：路由离开首页后若未 `disconnect()`，滚动到底会持续触发已卸载组件的加载函数。
7. **候选池上限被误当 bug**：滑到 200 条就没了是设计使然（C1），不是加载失败。终止文案要说清「已经到底了」。

## 七、验收方式

| # | 验收项 | 特征值 / 判据 |
|---|---|---|
| 1 | 首位配额生效 | 有类目偏好特征的登录用户，榜单前 5 条 `recallSource` 全为 `CATEGORY_PREF` |
| 2 | 配额可关闭 | `rank.head.personalized.size=0` 后，前 5 条恢复为融合顺序 |
| 3 | 冷启动降级 | 无特征用户前 5 条 `recallSource` 为 `HOT`，`degraded=冷启动`，无空位 |
| 4 | 坑位优先级 | 配一个 slot_position=1 的坑位，榜单第 1 条为坑位商品（`fixedSlot=true`），配额让位 |
| 5 | 无重复 | 触底追加全过程中，同一 `itemId` 不出现两次 |
| 6 | 顺序稳定 | 同一会话内触底续接，已展示条目的相对顺序不变 |
| 7 | 终止态 | 加载完 200 条后显示「没有更多了」，不再发请求 |
| 8 | 回归 | `mvn -pl shop-rec clean test` 5/5 通过 |
