# Phase 4 RAG 加固——需求文档

**背景**：本阶段两个主题：
- **A. 写操作安全**：`cancelOrder` 是写操作，目前 LLM 判断到就直接执行（仅靠工具 description 引导）。需加"取消前先确认"机制 + few-shot 示例，降低误操作风险。
- **B. RAG 四建议**：① 引用溯源（AI 回答标注依据商品）；② 索引联动（商品变更自动增量索引）；③ 可观测性（检索/生成指标采集）；④ 行为反馈（搜索→点击埋点，闭环评估）。

---

## ① 硬约束清单

### A. 写操作安全

- **C-A1**【文档明确规定】`cancelOrder` 调用前，LLM 必须**先向用户确认**订单信息（订单号/商品），用户明确确认后才调用工具；禁止未经确认直接取消。
- **C-A2**【文档明确规定】SystemPrompt 增加**工具调用 few-shot 示例**（查订单/查物流/取消订单的正确触发方式），引导 LLM 低误调率。
- **C-A3**【文档明确规定】确认引导用**简洁话术**（如"确认取消订单 #123 吗？"），不增加用户负担。
- **C-A4**【推导得出】确认机制是 **prompt 层引导**（LLM 行为约束），**不改变** `OrderTool.cancelOrder` 工具逻辑与 `OrderService` 服务层归属校验（服务层仍是最底安全线，C-A5 兜底）。
- **C-A5**【推导得出】即使 LLM 绕过确认直接调 `cancelOrder`，`OrderService` 的归属校验（非本人订单拒绝）仍生效——确认机制是"第一道防线"，服务层是"最后防线"。

### B. RAG 四建议

**B1 引用溯源**
- **C-B1-1**【文档明确规定】AI 回答推荐商品时，商品名后标注编号 `[1]`/`[2]`/`[3]`，编号**与 products 事件中商品顺序一致**。
- **C-B1-2**【文档明确规定】前端商品卡片左上角显示对应编号徽标，与 AI 回答的 `[n]` 对应。
- **C-B1-3**【推导得出】编号由 SystemPrompt 引导 LLM 生成（引用第 n 个商品时写 `[n]`）；products 事件商品顺序固定（RAG hits 顺序）。

**B2 索引联动**
- **C-B2-1**【文档明确规定】商品变更（新增 `addProduct`、状态变更 `updateStatus`）时，自动触发 `ProductIndexer.addOrUpdate` / `remove` 增量索引（项目**无改价功能**，用户已确认）。
- **C-B2-2**【文档明确规定】只做**增量联动**（变更商品才更新），**不改变**启动全量重建与 `forceRebuildAll` 既有逻辑。
- **C-B2-3**【推导得出】下架（status≠1 上架）→ `remove` 索引；新增/上架（status=1）→ `addOrUpdate` 索引。
- **C-B2-4**【文档明确规定】联动失败不影响商品主流程（吞异常 + `log.warn`，商品照常保存）。

**B3 可观测性**
- **C-B3-1**【文档明确规定】采集指标：检索 query / 检索耗时 / 向量命中数 / 关键词命中数 / LLM 调用 token 消耗 / LLM 耗时 / SSE 完成状态。
- **C-B3-2**【文档明确规定】指标采集**不记录 PII**（用户 ID 可记录，消息内容不记录）；不侵入业务主链路（轻量埋点 + 异步写日志）。
- **C-B3-3**【文档明确规定】指标可通过日志查看（`log.info` 汇总）或轻量监控接口（可选）。
- **C-B3-4**【推导得出】指标用于答辩说明"检索 P95 耗时、token 成本"等工程指标。

**B4 行为反馈**
- **C-B4-1**【文档明确规定】新增埋点：用户从搜索结果/客服卡片点击商品 → 记录 `(query, productId, action)` 到表。
- **C-B4-2**【文档明确规定】埋点**不阻塞主链路**（异步 + 吞异常，失败不影响点击/跳转）。
- **C-B4-3**【文档明确规定】数据可导出为评估集格式（query + 正例商品 ID），供扩充 `RagEvaluationTest`。
- **C-B4-4**【文档明确规定】首版来源：搜索结果页点击（轻量）；客服卡片点击可复用（可选增强）。

## ② 接口入参 / 出参 / 失败返回

### 2.1 写操作安全（A）——无新接口

- 改动点：`ChatService.SYSTEM_PROMPT_TEMPLATE` 增加"取消订单确认规则" + few-shot 示例；`OrderTool.cancelOrder` description 补充"需用户确认后才调用"。
- 失败返回：无（不改工具返回）。

### 2.2 引用溯源（B1）——无新接口，prompt + 前端

- 后端：SystemPrompt 增加"引用编号"规则（引用第 n 个商品写 `[n]`）。
- 前端：商品卡片加编号徽标（`recommendProducts` 下标 +1 显示）。
- 失败返回：无。

### 2.3 索引联动（B2）——内部调用

- **入参**：`ProductIndexer.addOrUpdate(ProductDO)` / `remove(Long productId)`
- **触发点**：`ProductServiceImpl.addProduct`（新增/更新后）、`updateStatus`（状态变更后）
- **失败返回**：`log.warn`，不抛给商品主流程（C-B2-4）。

### 2.4 可观测性（B3）——内部埋点（可选监控接口）

- 埋点：`RagSearchService.search()`（query/耗时/命中数）、`ChatService`（LLM token/耗时/SSE 状态）
- 可选：`GET /api/admin/rag/metrics` 返回汇总（token 消耗、平均耗时、命中率）
- 失败返回：监控接口异常返回空指标，不影响主链路。

### 2.5 行为反馈（B4）——新增埋点接口

- **入参**（JSON）：
  | 字段 | 类型 | 必填 | 约束 |
  |------|------|------|------|
  | `query` | String | 是 | 用户搜索词/客服推荐时的 query |
  | `productId` | Long | 是 | 用户点击的商品 |
  | `action` | String | 是 | 枚举：`SEARCH_CLICK`（搜索结果点击）|
- **出参**：`Result<Void>`（异步落库）
- **失败返回**：接口异常返回 `Result.error`，但**不影响**前端点击/跳转（前端异步调用 + 吞异常，C-B4-2）。

## ③ 风险翻车点清单

- **R-A1**：LLM 不遵守"先确认"规则，直接取消订单。触发条件：prompt 约束不强制/用户表达模糊。→ 缓解：SystemPrompt 强规则（"必须确认"）+ few-shot 示例 + 服务层归属校验兜底（C-A5）。
- **R-A2**：确认对话增加轮次，用户不耐烦。触发条件：确认话术过长。→ 缓解：确认简洁单句（C-A3）。
- **R-A3**：few-shot 示例与工具 description 冲突。触发条件：示例动作与 description 不符。→ 缓解：示例与 description 一致，T1 验收核对。
- **R-B1-1**：LLM 编号与卡片商品对不上。触发条件：LLM 引用商品但编号乱写。→ 缓解：prompt 强约束"引用第 n 个商品写 [n]" + 前端卡片编号按 hits 顺序。
- **R-B2-1**：商品变更频繁 → 索引频繁重建（成本）。触发条件：高并发改商品。→ 缓解：仅变更商品增量更新，非全量。
- **R-B2-2**：商品变更入口未全部覆盖（如漏了某状态/新增路径）。触发条件：存在未埋点的商品变更路径。→ 缓解：T3 先盘点 `addProduct` / `updateStatus` 的全部调用路径（已确认项目**无改价/删除方法**）。
- **R-B3-1**：指标采集影响性能。触发条件：埋点阻塞主链路。→ 缓解：异步 + 轻量（C-B3-2）。
- **R-B4-1**：无真实流量攒不出数据。触发条件：项目无真人使用。→ 缓解：演示时手动触发/ mock；数据表结构先就位（C-B4-4）。
- **R-B4-2**：埋点接口被滥用（刷数据）。触发条件：接口未限流。→ 缓解：登录用户才可上报（复用登录态），首版从简。
