# 001 评估集重建与 ES 关键词路效果评估（2026-10-21）

> 关联：`spec.md` / `design.md` / `plan.md`
> 被测链路：向量路（TEI/BGE-M3 + Qdrant）+ 关键词路（ES BM25+IK 或 MySQL FULLTEXT）→ 加权 RRF
> 复现命令：`mvn -pl shop-server test -Dtest=RagEvaluationTest -Dsurefire.failIfNoSpecifiedTests=false`

## 一、为什么要重建评估集

旧评估集（2026-08 标注，30 条）的期望 ID 已与当前商品数据完全脱节：

| query | 旧期望 ID | 当前实际商品 |
|-------|----------|-------------|
| 口红 | 2 / 29 / 30 / 43 | 小米手机 / 南极人被芯 / 晨光中性笔 / 保暖内衣 |
| 剃须刀 | 34 | 联想轻薄笔记本（且已下架） |
| 手机 | 1 / 12 / 16 | 华为手机 / 雅诗兰黛精华 / 得力文件柜 |

用**改动前代码**跑旧评估集，Recall@3 也只有 **0.033**（30 条命中 1 条）——说明是评估集失效，不是检索退化。旧指标（0.711 / 0.753 / 0.474）在评估集重建前不可用于对比。

## 二、新评估集设计

### 2.1 数据基线

| 项 | 值 |
|----|-----|
| 上架商品 | 670 |
| 一级分类 | 8 个（手机数码 157 / 家居家装 94 / 家用电器 93 / 食品生鲜 90 / 服装鞋包 78 / 美妆个护 71 / 母婴玩具 61 / 图书文娱 26） |
| 问题 | mock 数据中同一商品有多个重复 SPU（如「晨光中性笔」有 16 个 ID），因此期望集必须取**同类商品全集** |

### 2.2 标注口径

1. 期望集 = 该 query 相关的**全部上架商品 ID**，由 SQL 按商品名聚合生成（不取代表，避免「召回同名商品却判不中」）；
2. 主指标改为 **Hit@K**（top-K 是否至少命中一个）与 **MRR@FirstHit**（首个命中位置）；
3. Recall@5 仅作参考：期望集 39 个时 Recall@5 上限只有 5/39≈0.128，不能横向比较。

### 2.3 用例分布（37 条正样本 + 3 条负样本）

| 类型 | 数量 | 示例 |
|------|------|------|
| 精确型号 / 商品名 | 6 | 戴森 V12 吸尘器、松下剃须刀、华为 Mate 60 |
| 品类词 | 10 | 手机、吸尘器、跑步鞋、纸尿裤、帐篷、冰箱 |
| 品牌词 | 6 | 华为、小米、苹果 iPhone、戴森、飞利浦、乐高 |
| 口语化 / 同义词 | 6 | 充电宝、刮胡刀、球鞋、笔记本电脑、口红、婴儿车 |
| 错别字 / 长句 | 5 | 手鸡、洗依机、打游戏手机、给刚出生的宝宝买奶粉 |
| 属性组合 | 4 | 4L 电饭煲、L 码纸尿裤、550ml 矿泉水、轻薄本 |
| 负样本（不计指标） | 3 | 吉他、钢琴、墨镜（库中无对应商品） |

## 三、结果

### 3.1 基础集（37 条）

| 阶段 | Hit@3 | Hit@5 | MRR@FirstHit | Recall@5（参考） |
|------|-------|-------|--------------|------------------|
| 初始（RRF 1.0/2.0） | 0.973 | 0.973 | 0.959 | 0.465 |
| **最终（RRF 1.0/1.5 + 错别字纠正）** | **1.000** | **1.000** | **0.986** | 0.484 |

两处改进：
- RRF 权重 2.0 → 1.5（§3.4），MRR 0.959 → 0.973；
- 单向错别字纠正（§4.3），「手鸡」「洗依机」从 0 命中变为 Hit@3=1，整体 Hit@3 → 1.000。

### 3.2 关键词引擎对照（向量路固定不变）

| 关键词路 | Hit@3 | Hit@5 | MRR |
|---------|-------|-------|-----|
| MySQL FULLTEXT（ngram） | 0.946 | 0.973 | 0.926 |
| **Elasticsearch（BM25 + IK）** | **0.973** | 0.973 | **0.959** |
| 差值 | **+0.027** | 0 | **+0.034** |

结论：在新数据上 ES 略优于 FULLTEXT（多命中 1 条、排序更靠前），但**差距远小于预期**——因为 37 条用例里大部分是精确词/品类词，两条路都能命中；差距主要体现在排序质量（MRR）。

### 3.3 同义词扩展对照（5 条）

| 配置 | Hit@3 | Hit@5 | MRR |
|------|-------|-------|-----|
| 关闭扩展 | 0.800 | 1.000 | 0.840 |
| 开启扩展 | **1.000** | 1.000 | **1.000** |
| 变化 | +0.200 | 0 | **+0.160** |

同义词扩展（`rag.synonym`）价值明确：口语词从「第 2~3 位命中」提升到「首位命中」。

### 3.4 加权 RRF 对照（37 条）

| 权重（wv / wk） | Hit@3 | Hit@5 | MRR |
|----------------|-------|-------|-----|
| 1.0 / 1.0 | 0.973 | 0.973 | **0.973** |
| 1.0 / 1.5（**已设为生产值**） | 0.973 | 0.973 | **0.973** |
| 1.0 / 2.0（原生产值） | 0.973 | 0.973 | 0.959 |

**原生产档位 2.0 在新数据上不是最优**：关键词权重过高会放大 ES `operator: OR` 的宽泛匹配，压制向量路的语义结果（典型表现是「手鸡」这类 query 被无关商品挤占）。已回调至 **1.5**。

### 3.5 负样本行为（不计指标）

| query | 检索返回 top-3 | 判断 |
|-------|---------------|------|
| 吉他 | 雅马哈电子琴 / 李宁羽毛球拍 / 雷蛇键盘 | 语义相近品类，可接受但偏宽 |
| 钢琴 | 雅马哈电子琴 / 飞利浦牙刷 | 电子琴合理，牙刷不合理 |
| 墨镜 | 晨光文具 / 得力中性笔 | **明显硬凑** |

补充实测：ES 关键词路对「墨镜」返回 **0 条**、对「吉他」返回 0 条——上述结果是**向量路**返回的，说明 `rag.search.min-relevance-score=0.3` 对无关 query 放行过宽。属既有问题，非本次改造引入。

## 四、发现与建议

### 4.1 RRF 权重建议回调（需拍板）

把 `rag.rrf.weight-keyword` 从 **2.0 改为 1.5**：
- 新数据实测 MRR 0.959 → 0.973；
- 1.5 与 1.0 指标持平，但保留关键词路一定话语权（对字面强匹配 query 有利）；
- ⚠️ 该值来自旧数据评估（Recall@3 0.628→0.711），换数据后需要重新权衡，不能直接沿用。

### 4.2 ES `operator: OR` 噪声（已验证：不启用门槛，保持 OR）

「手鸡」在纯 OR 下命中 9 条噪声，第一名是「帮宝适婴儿手口湿巾」（BM25 18.7）——IK 把未登录词切成「手 / 鸡」单字，OR 让任一单字命中即通过。

实测三档门槛（37 条完整评估集）：

| 模式 | Hit@3 | Hit@5 | MRR |
|------|-------|-------|-----|
| OR（无门槛） | **0.973** | 0.973 | **0.973** |
| `2<70%` | 0.892 | 0.946 | 0.904 |
| `100%`（AND） | 0.946 | 1.000 | 0.945 |

**提高门槛反而更差**。典型误伤是「轻薄本」：IK 切成「轻薄」「本」，门槛要求「本」也命中，而商品名是「轻薄笔记本」，导致完全 0 命中。

结论：保持纯 OR；`rag.elasticsearch.minimum-should-match` 配置项保留但**默认置空**。
注意评估集只衡量「是否命中」，不惩罚「结果里混入噪声」——OR 的噪声问题在指标上不可见，
若线上出现噪声投诉，应针对**具体 query 长度分档**再调，而不是全局提高门槛。

### 4.3 错别字：已用单向纠正兜底，LLM 改写是后续方向

实测两条关键词路都没有错别字容错：

| 引擎 | 「手鸡」命中数 | 原因 |
|------|--------------|------|
| MySQL FULLTEXT（ngram n=2） | 0 | 「手鸡」是一个 2-gram，索引里没有 |
| ES（IK） | 9（全是噪声） | IK 切成单字 + OR 放大 |

**已实现**：`rag.synonym.corrections` 单向错别字纠正（错 → 对），当前覆盖
「手鸡 → 手机」「洗依机 → 洗衣机」。效果：两条 query 的 Hit@3 从 0 提升到 1，
基础集整体 Hit@3 0.973 → **1.000**、MRR 0.959 → **0.986**。

实现要点：
- 必须**单向**（错 → 对）。若放进双向同义词组，搜「手机」时也会混入「手鸡」，反而制造噪声；
- 配置用 `List<List<String>>` 而非 `Map`：Spring Boot 的 `ConfigurationPropertyName`
  不接受中文 Map key，绑定期会报 `ConverterNotFoundException`（实测踩坑）。

**局限与后续（LLM 改写）**：
- 规则表是人工兜底，覆盖有限，新错别字需补充；
- 更通用的方案是 **LLM query 改写**：项目已有 `QueryRewriter`，但当前只在智能客服链路调用，
  公开搜索接口 `/api/product/rag-search` 不走改写，且 Prompt 未明确要求纠正错别字；
- 推荐**两阶段**而不是每次搜索都调 LLM：规则层先跑（微秒级、零成本）→ 检索 →
  「结果为空或 top1 分数低」时才调 LLM 改写重试（秒级、有成本）。原因是商品搜索高频，
  每次 1~3 秒的 LLM 延迟不可接受，且 LLM 可能把「手鸡」改成「手工鸡」，需要规则层兜底；
- 注意区分：`ChatIntentResolver` 做的是**意图识别**（查订单 / 取消 / 搜索），不是纠错。

### 4.4 评估集维护

期望 ID 依赖商品数据。**商品数据重构后必须重新生成**，否则会重演本次「指标全 0 却误以为检索坏了」的问题。生成 SQL：

```sql
-- 每个概念一条，GROUP_CONCAT 出全集
SELECT GROUP_CONCAT(id ORDER BY id)
FROM shop.product
WHERE status = 1 AND deleted = 0 AND name LIKE '%关键词%';
```

## 五、结论

1. 新评估集可用：**最终 Hit@3=1.000 / MRR=0.986**，检索链路在真实数据上工作正常；
2. ES 相比 FULLTEXT 有小幅提升（Hit@3 +0.027、MRR +0.034），主要收益在**排序质量与
   过滤下推**，不在命中率；
3. 同义词扩展的收益（MRR +0.160）大于换引擎；
4. 本轮已落地三项：**RRF 权重 2.0 → 1.5**、**单向错别字纠正**、**ES 匹配门槛保持 OR**；
5. 后续方向：把错别字/长句纠错上移到 LLM query 改写层，按「检索置信度低」两阶段触发
   （见 §4.3），这是比继续扩规则表更通用的路径。
